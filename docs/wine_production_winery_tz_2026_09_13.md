## 1. Зачем

Бренд может не иметь своего производства и собирать вино у разных хозяйств.
Сейчас в каталоге это не выразить: у вина одна винодельня.

Живой пример на 13.09.2026:

| Вино | Винодельня в каталоге | Линейка | География вина |
|---|---|---|---|
| Tussock Jumper Tempranillo | Tussock Jumper Wines (несколько стран) | Tussock Jumper | Испания · Кастилия и Леон |
| Tussock Jumper Chardonnay | Orchidées, Maisons de Vin (Франция) | — | Франция · Лангедок |

Одно вино записано на бренд, и хозяйство потеряно. Второе записано на
хозяйство, и выпало из бренда: его нет ни на странице Tussock Jumper Wines,
ни в линейке. Выбрать между этими вариантами нельзя, нужно оба сразу.

Цель: у вина остаётся одна винодельня карточки (бренд). Появляется
необязательная ссылка на хозяйство, где его сделали. Хозяйство —
обычная каталожная винодельня со своим описанием, контактами и географией.

## 2. Термины

- **Винодельня вина** (`wines.winery_id`, как сейчас) — чьё это вино для
  человека: бренд, проект, автор. Её имя на этикетке крупно, по ней вино ищут,
  под ней живут линейки.
- **Хозяйство-производитель** (новое, `wine_production_partners.winery_id`) —
  винодельня, которая физически сделала вино для бренда. Необязательно.
- **Линейка** — серия внутри винодельни вина. Не меняется: линейка ≠
  хозяйство-производитель.

Не являются хозяйством-производителем и сюда не записываются:

- разливщик без собственного виноделия, импортёр, дистрибьютор, магазин;
- юрлицо из поля «Производитель» у винодельни (`wineries.producer` — текст
  «ООО … (ИНН)» из реестра, 297 записей). Это реквизит той же винодельни, а не
  другая винодельня;
- производственная площадка **той же** компании — это точка винодельни
  (`winery_locations`, тип `production`, ТЗ от 12.07.2026 §10), а не
  отдельная запись.

Правило различения: если у площадки своё имя, своя история и она работает на
несколько брендов — это хозяйство-производитель. Если это адрес цеха самого
бренда — точка винодельни.

## 4. Решения

**Р1. Хозяйство вина — в отдельной таблице.** `wine_production_partners`
со своим ключом `id`. В срезе 1 у вина не больше одного хозяйства
(уникальность `wine_id`), но схема сразу готова к нескольким: ограничение
снимается без смены таблицы и без поломки 1.1.0 (§8, вариант G). Связи
«бренд ↔ хозяйства» напрямую не заводим: хозяйство меняется от вина к вину, и
список партнёров бренда вычисляется из его вин.

Почему не колонка `wines.production_winery_id`: вторая связь `wines → wineries`
делает неоднозначным запрос `wineries(*)` без имени связи. Так PostgREST ведёт
себя при двух внешних ключах между одной парой таблиц, ошибка `PGRST201`.
Такой запрос шлют десятки выборок приложения и **уже установленное 1.1.0**,
исправить его в сторах нельзя. Отдельная таблица оставляет у `wines` одну связь
с `wineries`. Проверено 13.09.2026 на PostgREST v14.8, §8.

**Р2. Хозяйство — винодельня с одним местом.** Хозяйством-производителем может
быть только винодельня с охватом «одно место» (`single`), не удалённая и не
объединённая. Бренд с «Несколько стран» хозяйством быть не может, иначе
получаются цепочки «бренд у бренда».

**Р3. Хозяйство ≠ винодельня вина.** Проверяется триггером: связь таблиц,
ограничение `check` на это не способно.

**Р4. Кому можно.** Любой винодельне вина, не только мультирегиональной.
Пример: российский бренд, который разливает вино на чужом заводе.

**Р5. География не наследуется в базе.** Цепочка чтения остаётся прежней:
своя страна и регион вина, потом винодельни вина. Хозяйство только
**подставляет** страну и регион в форму, если у вина они пустые. Сохраняются
явные значения. Так ни один из 28 читателей `wines.winery_id` не меняет логику
географии.

**Р6. Фильтр «Винодельня» в каталоге находит оба.** Выбор Orchidées в фильтре
показывает и её собственные вина, и вина, сделанные ею для брендов. Человек,
который ищет хозяйство, ожидает увидеть Tussock Jumper Chardonnay.
*Решено владельцем 13.09.2026.*

**Р7. Перенос вина — отдельное действие с историей.** Сейчас винодельня вина
задаётся маршрутом редактора, и сменить её у одного вина нельзя. Объединение
дублей для этого не подходит: оно переносит все вина. Появляется «Перенести в
другую винодельню» с опцией «оставить прежнюю как хозяйство-производитель».

**Р8. Перенос не меняет происхождение вина.** Если у вина нет своих страны и
региона, перед переносом в них записываются значения прежней винодельни.
Сменился бренд на этикетке, а не место, где выросло вино.

**Р9. Совместимость с 1.1.0.** Только добавочные изменения. Старое приложение
новой таблицы не запрашивает; выборки `wines.winery_id` не меняются.

## 5. Модель данных

```sql
-- Ключ — только id. Составной первичный ключ (wine_id, winery_id) PostgREST
-- принимает за «многие ко многим» и ломает wineries(*) у 1.1.0 (§8).
create table public.wine_production_partners (
  id uuid primary key default gen_random_uuid(),
  wine_id uuid not null references public.wines(id) on delete cascade,
  winery_id uuid not null references public.wineries(id) on delete restrict,
  source text not null default 'moderator'
    check (source in ('moderator', 'research', 'move', 'merge')),
  actor_user_id uuid references public.profiles(id),
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

-- Срез 1: одно хозяйство на вино. Снять — когда появится реальный случай (§14).
alter table public.wine_production_partners
  add constraint wine_production_partners_one_per_wine unique (wine_id);
alter table public.wine_production_partners
  add constraint wine_production_partners_pair_key unique (wine_id, winery_id);

create index wine_production_partners_winery_idx
  on public.wine_production_partners(winery_id);

comment on table public.wine_production_partners is
  'Хозяйство, которое сделало вино для бренда (wines.winery_id). Пока одно на вино (wine_production_partners_one_per_wine). Только винодельня с одним местом.';
```

Чтение — всем, как у `wine_lines`. Запись — только через RPC
`admin_set_wine_production_winery(p_wine_id, p_winery_id)` (`null` снимает
связь) и RPC переноса 6.1. Прямой записи из клиента нет: те же правила
каталога, что у `wines`.

Проверки Р2 и Р3 — триггер `validate_wine_production_partner` на таблице:

- хозяйство существует, `geography_scope = 'single'`, не `is_deleted`,
  `merge_status = 'active'` → иначе `wine_production_winery_invalid`;
- хозяйство ≠ `wines.winery_id` → иначе `wine_production_winery_is_owner`.

Смежные триггеры:

- на `wines` при смене `winery_id`: если новая винодельня совпала с
  хозяйством, строка связи удаляется;
- на `wineries` при переводе в «Несколько регионов» или «Несколько стран»:
  если винодельня указана хозяйством, ошибка `winery_is_production_partner`
  (сначала снять связи).

Аудит переноса:

```sql
create table public.wine_winery_moves (
  id uuid primary key default gen_random_uuid(),
  wine_id uuid not null references public.wines(id) on delete cascade,
  from_winery_id uuid not null references public.wineries(id),
  to_winery_id uuid not null references public.wineries(id),
  previous_production_winery_id uuid references public.wineries(id),
  previous_line_id uuid references public.wine_lines(id) on delete set null,
  previous_country_code varchar(2),
  previous_region_id uuid,
  kept_as_production boolean not null,
  actor_user_id uuid not null references public.profiles(id),
  notes text,
  created_at timestamptz not null default now()
);
```

Чтение — только каталожным админам (RLS как у `winery_merge_actions`).

## 6. Серверные правила

### 6.1. RPC переноса вина

`admin_move_wine_to_winery(p_wine_id uuid, p_target_winery_id uuid,
p_keep_previous_as_production boolean, p_target_line_id uuid default null,
p_notes text default null) returns jsonb`

Порядок в одной транзакции:

1. Проверка: `is_catalog_admin`, вино и целевая винодельня активны, цель ≠
   текущая.
2. Материализация географии по Р8 (страна и регион прежней винодельни, только
   в пустые поля).
3. `line_id`: если передан `p_target_line_id`, он должен принадлежать цели.
   Иначе старая линейка снимается, если она не принадлежит цели.
4. Связь с хозяйством: при `p_keep_previous_as_production` — прежняя
   винодельня, `source = 'move'` (проверка Р2; если прежняя
   мультирегиональная — ошибка с понятным кодом). Если прежнее хозяйство
   совпало с целью — связь удаляется.
5. Строки `winery_profile_featured_wines` прежней винодельни: остаются, если
   она стала хозяйством (см. 6.4), иначе удаляются.
6. Запись в `wine_winery_moves`, ответ `{wine_id, from, to, line_cleared,
   geography_materialized}`.

Отмена переноса в первом срезе не делается. Истории достаточно, чтобы
вернуть вино руками.

### 6.2. Объединение дублей

`admin_merge_wineries(S → T)` дополнительно:

- `update wine_production_partners set winery_id = T where winery_id = S`;
- строки, где T стала винодельней самого вина, удаляются;
- id затронутых вин — в новую колонку
  `winery_merge_actions.retargeted_production_wine_ids uuid[]`, удалённые
  строки — в `removed_production_links jsonb`.

`admin_unmerge_winery` возвращает эти ссылки на S и восстанавливает удалённые.
Если S указана хозяйством, а T мультирегиональная, объединение запрещено
ошибкой `merge_target_not_single_for_production`.

### 6.3. Удаление винодельни

Мягкое удаление (`is_deleted`) хозяйства, на которое ссылаются вина,
запрещено ошибкой `winery_is_production_partner` с числом вин. Для админа это
понятнее, чем тихо исчезнувшая строка «Произведено» у чужих вин.

### 6.4. Ключевые вина публичной страницы

`validate_winery_featured_wine_v1`: вино подходит, если
`w.winery_id = new.winery_id` или есть строка `wine_production_partners`
с `wine_id = new.wine_id` и `winery_id = new.winery_id`.

### 6.5. Каталог и фильтры (Р6)

- `get_wines_with_filters_and_sorting`: условие по `p_winery_ids` —
  `w.winery_id = any(...)` или `exists` строки в `wine_production_partners`
  с `winery_id = any(...)`;
- `get_available_wineries`: хозяйства вин с активными предложениями тоже
  попадают в список;
- в выдаче вина винодельня карточки остаётся прежней.

### 6.6. Остальные читатели

Аудит 13.09.2026 на бою: 28 функций и 2 вьюхи читают `wines.winery_id`.
Кроме 6.2–6.5, логику менять не нужно: связь `wines → wineries` остаётся
одной.

Хозяйство для карточки вина:

- выборка карточки в `wines_repository` добавляет embed
  `wine_production_partners(winery:wineries(id, name, country_code, region_id,
  country:countries(code, name), region:regions(id, name)))`. Имя связи
  указывается явно — на случай, если PostgREST увидит в таблице связь
  «многие ко многим» (§8);
- `get_user_storage`, `get_user_tastings`, `add_user_tasting`,

### 7.2. Карточка вина (покупатель)

Пожелание владельца 13.09.2026: по карточке сразу видно, что вино бренда
сделано в хозяйстве, и можно прочитать про обоих.

Нет хозяйства — карточка выглядит как сейчас. Всё ниже появляется только при
наличии хозяйства-производителя.

**Шапка.** Сейчас над названием одна строка «винодельня · линейка»
(`wine_card_hero.dart` → `_WineryLine`, строка `wineDetailsHeroWineryLine`).
Становится цепочкой в две строки того же стиля:

```text
TUSSOCK JUMPER WINES · ЛИНЕЙКА «TUSSOCK JUMPER»
ХОЗЯЙСТВО ORCHIDÉES, MAISONS DE VIN
Tussock Jumper Chardonnay
🇫🇷 Франция · Лангедок
```

- Первая строка — бренд и линейка, как сейчас. Линейка стоит рядом с брендом,
  а не после хозяйства: это серия бренда. Схема «бренд · хозяйство · линейка»
  читалась бы как линейка хозяйства.
- Вторая строка — хозяйство, приглушённым золотом (`WineCardTokens`, без
  прямых цветов). Нажатие прокручивает карточку к блоку «Винодельни».
- Длинные имена: каждая строка в одну строку с многоточием, полное имя —
  в `Semantics` и в блоке ниже.
- `_WineryLine` получает параметр `productionWineryName`, вторую копию шапки
  не заводим (правило 2).

**Блок «Винодельня» → «Винодельни».** Сейчас одна карточка
(`wine_winery_spotlight_section.dart`: логотип, имя, число вин, начало
описания, баннер). С хозяйством — две карточки друг под другом, вторая
вложена в первую:

```text
ВИНОДЕЛЬНИ
┌──────────────────────────────────────────┐
│ [лого]  Tussock Jumper Wines              │  подпись «Бренд»
│         Несколько стран · 2 вина          │
│         Tussock Jumper — международный…   │
└──────────────────────────────────────────┘
   │  вино сделано в хозяйстве
   └─┌───────────────────────────────────────┐
     │ [лого]  Orchidées, Maisons de Vin      │  подпись «Хозяйство»
     │         Франция · Лангедок · 1 вино    │
     │         Семейный дом в Лангедоке…      │
     └───────────────────────────────────────┘
```

- Одна карточка-виджет с параметрами, а не две разные: `roleLabel`
  («Бренд» / «Хозяйство»), `indent`, `showConnector`. Без хозяйства —
  параметров нет, вид прежний, заголовок «Винодельня».
- Связка между карточками — тонкая линия цвета `WineCardTokens.hairline` с
  подписью «вино сделано в хозяйстве». Это единственный пояснительный текст,
  он передаёт отношение, а не инструкцию.
- География в карточке — через `wineryGeographyLine`: у бренда «Несколько
  стран», у хозяйства «Франция · Лангедок».
- Число вин у хозяйства считает и вина, сделанные для брендов (как фильтр,
  Р6). Источник — `wine_card_discovery_provider.dart`, в нём добавляется
  счётчик для хозяйства.
- Нажатие на каждую карточку делает то же, что сейчас: открывает каталог с
  фильтром по этой винодельне. Переход на страницу винодельни — отдельное
  решение для обеих карточек сразу, не в этой задаче.
- Начало описания — у обеих карточек, так «можно прочитать про всех» не
  уходя с карточки вина.

Подписи на четырёх языках: «Бренд», «Хозяйство», «Винодельни», «Хозяйство
{name}», «вино сделано в хозяйстве».

### 7.3. Страница винодельни в приложении

- У бренда — блок **«Хозяйства-производители»**: хозяйства его вин, у каждого
  география и число вин. Нажатие — страница хозяйства.
- У хозяйства — блок **«Производит для брендов»**: бренды и число вин, нажатие
  — страница бренда. Список «Вина винодельни» показывает и эти вина с пометкой
  бренда.
- Данные — одна RPC `get_winery_production_links(p_winery_id)` →
  `{partners: [...], brands: [...]}`, только публичные вина.

### 7.4. Разбор заявки

- В блоке «Винодельня», после выбора или создания винодельни, — поле
  **«Хозяйство-производитель»**. Тот же виджет, что в 7.1, с параметром
  контекста, а не копией (правило 2).
- Подсказка из исследования AI: кандидаты с ролью `production_winery` и
  уверенностью от 0,7 ищутся в каталоге по имени и псевдонимам. Нашлось —
  чип «Orchidées, Maisons de Vin» одним нажатием. Не нашлось — чип
  «Создать хозяйство», который открывает создание винодельни с охватом «одно
  место» и именем кандидата.
- Значение уходит в редактор вина вместе с черновиком (параметр маршрута
  рядом с `initialWine`; редактор после сохранения вина зовёт
  `admin_set_wine_production_winery`) и в
  решение нормализации: раздел `production_winery` с `raw_value`,
  `resolved_id`, `decision_kind`.

### 7.5. Исследование AI

- Результат разрешения ролей сохраняется в отчёт: `identity_roles` —
  массив `{name, role, confidence, reason}`. Сейчас он живёт только в промпте.
- Правило промпта не меняется: бренд — винодельня карточки, хозяйство —
  отдельной ролью, разливщик хозяйством не предлагается.

### 7.6. Публичная веб-страница винодельни

`get_public_winery_page_v1`: блоки 7.3 в ответе (`production_partners`,
`produces_for`). Делается третьим срезом, после туристического пилота, —
очередь §8 `winery_unified_model_2026_09_07.md` не сдвигается.

## 14. Вне рамок

- Несколько хозяйств у одного вина. Схема готова (§5, вариант G), а
  экраны и правила — нет. Что это даёт на практике, §14а.
- Разливщик, импортёр, дистрибьютор как роли вина.
- Распознавание «Produced and bottled by …» с этикетки — отдельной задачей в
  линии разбора этикетки.
- Сопоставление чеков по имени хозяйства: в чеках пишется бренд.
- Коллекции (этап 2 `wine_collections_concept_2026_06_14.md`).

## 14а. Когда у вина бывает несколько хозяйств

Обычно конкретное вино делает одно хозяйство, поэтому срез 1 держит одно.
Варианты, при которых хозяйств становится больше:

1. **Хозяйство меняется от урожая к урожаю.** Бренд вроде Tussock Jumper
   может сделать Tempranillo 2023 у одного партнёра, а 2024 — у другого.
   Самый вероятный случай. Правильная модель здесь — хозяйство у **выпуска**
   (`wine_vintages`), а не два хозяйства у вина одновременно: необязательная
   колонка `wine_vintage_id` в той же таблице. Перед этим — повторная проверка
   §8: у `wine_vintages` своя связь с `wines`, и путь через таблицу нужно
   проверить заново.
2. **Купаж из вин двух хозяйств**, собранный брендом. Редко, но бывает. Здесь
   нужны именно два хозяйства у вина.
3. **Виноград от нескольких виноградарей, а вино делает одно хозяйство.** Это
   одно хозяйство: поставщики винограда хозяйствами-производителями не
   считаются и не записываются.

Отказ от 1.1.0 для этого не нужен. Механизм принудительного обновления
в проекте есть (`app_release_config.min_supported_build_number`,
`app_update_provider.dart`), но пригодится для других причин.
