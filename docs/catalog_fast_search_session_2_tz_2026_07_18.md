## 1. Цель

Собрать единый бесплатный путь поиска и изучения вина по собственному каталогу
для текста, штрихкода и фотографий этикетки. Пользовательский UX должен явно
показывать эти каналы как три равноправных способа найти существующее вино, а не
прятать штрихкод и этикетку только внутри намерения `Добавить бутылку`. Поиск не
вызывает AI и внешние search API, переиспользует существующие receipt/label
matcher, нормализацию, aliases, lexicons, memory и explainable ranking.

Одновременно устранить ограничение `wines.barcode`: поддержать несколько товарных
кодов, коды конкретных выпусков и будущий точный учёт коллекции, не превращая
Сессию 2 в полную реализацию Cellar Pro.

## 3. Зафиксированные продуктовые решения

### 3.1. Не создавать новый matcher

Единый application-фасад адаптирует существующий receipt matcher и репозитории.
Новые эвристики допускаются только как явно протестированная общая policy
`exact/candidates/no reliable match`, а не как отдельный алгоритм одного экрана.

### 3.2. Разделить четыре уровня идентичности

```text
Wine (устойчивая идентичность продукта)
  -> Wine vintage/release (конкретный год или NV)
       -> Personal acquisition lot (партия пользователя; текущий user_storage)
            -> Bottle instance (физическая бутылка; Cellar Pro P3)
```

Штрихкод производителя определяет продукт/выпуск/вариант упаковки, но не
физический экземпляр пользователя. Внутренний WinePool QR/NFC будущего Cellar Pro
определяет конкретный `bottle_instance` и не смешивается с EAN/UPC/GTIN.

### 3.3. Один пользовательский flow, два уровня детализации

Не вводить роль `коллекционер` и не спрашивать её при регистрации/onboarding.
Использовать настройку представления:

- `quick` — основные поля и быстрое добавление;
- `detailed` — выпуск, формат, provenance, питьевое окно, место и дополнительные
  сведения по мере появления соответствующих модулей.

Настройка влияет только на UI. Matcher, каталог, storage contract и права доступа
остаются едиными. Предложение включить подробный учёт показывается контекстно
после использования винтажа, нескольких бутылок, формата или места хранения.
Entitlement Cellar Pro хранится отдельно и не ограничивает доступ пользователя к
собственным базовым данным.

### 3.4. Термины: вино, релиз и винтаж

- `Wine` — устойчивая базовая карточка линейки вина.
- `Release` — конкретная коммерческая версия вина, к которой относятся фото,
  товарные коды, алкоголь, состав и другие изменяемые характеристики.
- `Vintage` — год урожая и один из ключевых атрибутов релиза; `NV` означает
  невинтажный релиз, а не неизвестный год.
- каждый винтаж `2022`, `2023`, `2024` и т. д. создаётся отдельным релизом, даже
  если название и этикетка не изменились;
- один релиз не объединяет несколько винтажей;
- для одного винтажа допускаются несколько релизов только при реальном различии
  коммерческих версий (рынок, специальное издание, новая этикетка и т. п.);
- у `NV` также могут существовать разные релизы, различаемые названием выпуска,
  периодом выхода, фотографиями и товарными кодами.

Текущая таблица `wine_vintages` исторически названа по винтажам, но в предметной
модели выполняет роль `Wine release`, где `vintage` — атрибут записи.

## 4. Минимальный каталожный фундамент

### 4.1. `wine_vintages`

Additive-дочерняя сущность конкретного выпуска:

```text
id, wine_id, vintage nullable, is_non_vintage,
release_name nullable, description nullable, alcohol_level nullable,
grape_composition nullable, characteristics, quality_status,
source_payload, created_at, updated_at
```

Правила:

- ровно одно: конкретный `vintage` либо `is_non_vintage = true`;
- `vintage unknown` представлен отсутствием ссылки на profile, а не `NV`;
- существующие `offers.vintage`, `user_storage.vintage`, tastings и reviews
  продолжают работать без обязательного backfill;
- profile хранит overrides, стабильные значения остаются в `wines`;
- отсутствие profile не блокирует поиск и добавление бутылки;
- AI и пользователь не публикуют profile автоматически.

### 4.2. `wine_product_codes`

Отдельная additive-таблица вместо массива или дополнительных колонок в `wines`:

```text
id, wine_id, wine_vintage_id nullable,
code, normalized_code, code_type,
bottle_volume_ml nullable, package_kind nullable,
market_country_code nullable, status, is_primary,
provenance, created_at, updated_at
```

Поддерживаются:

- несколько кодов одного вина;
- несколько кодов одного выпуска;
- разные коды разных выпусков;
- код базового wine, когда выпуск неизвестен;
- различия объёма, рынка и упаковки;
- pending/conflicted/archived связи.

Стартовые статусы: `verified`, `legacy`, `user_submitted`, `pending`, `conflicted`,
`archived`. Точный набор фиксируется миграцией.

`wines.barcode` в Сессии 2 не удаляется. Непустые legacy-значения переносятся в
новую таблицу идемпотентно; чтение временно сохраняет fallback. Новые записи
должны идти через единый product-code write path.

Не вводить безусловный `UNIQUE(normalized_code)`: текущие дубли и спорные связи
должны быть наблюдаемы. Нельзя иметь несколько активных подтверждённых владельцев
кода после модерационного решения; конфликт не считается exact match.

## 5. Единый поисковый контракт

Концептуальные типы:

```text
CatalogSearchInput
  channel: text | barcode | label
  text/barcode
  labelCaptures[]
  requestId

LabelCapture
  role: front | back | barcode | other
  OCR text
  detected product codes
  source metadata

CatalogSearchCandidate
  wine
  optional vintage profile
  optional product code
  optional bottle volume/package
  score
  matched signals
  verify signals
  hard mismatch

CatalogSearchResult
  outcome: exact | candidates | noReliableMatch | conflict | error
  candidates
  normalized diagnostics
```

В пользовательскую аналитику не отправлять сырой OCR-текст и полный поисковый
запрос.

## 6. Policy исходов

### Barcode

- ровно одна активная подтверждённая связь с конкретным релизом -> `exact`
  этого релиза;
- общая подтверждённая связь (`wine_vintage_id is null`) определяет вино, но
  не винтаж: пользователь явно выбирает один из существующих релизов;
- варианты выбора показываются чипами (`2024`, `2023`, `NV`), а не сообщением
  о «нескольких винтажах»; дополнительно доступны `Не вижу год` и
  `Нет нужного года`;
- распознанный OCR год может быть только рекомендованным значением. Источник
  изображения может не соответствовать бутылке пользователя, поэтому явный
  выбор пользователя всегда имеет приоритет;
- `Не вижу год` не превращается в `NV`: в первом случае бутылка остаётся без
  подтверждённого релиза, во втором выбирается реальный NV-релиз каталога;
- `Нет нужного года` открывает существующий сценарий предложения релиза с
  уже известными вином и GTIN;
- несколько активных связей -> `conflict`, показать кандидатов;
- только pending/conflicted связи -> кандидаты либо `noReliableMatch`;
- отсутствие связи -> `noReliableMatch` и существующий draft-flow.

Одинаковый GTIN, наблюдавшийся на нескольких релизах одного вина, сам по себе
не является конфликтом между винами. Каноническая общая связь хранится на
уровне `wine_id`; релиз выбирается пользователем либо подтверждается отдельной
однозначной связью. Один GTIN не должен молча назначаться разным каноническим
винам.

### Text/label

`exact` требует одновременно:

- score выше калиброванного порога;
- отсутствует hard mismatch;
- присутствует сильный identity signal;
- разрыв с кандидатом №2 достаточен.

Иначе результат — `candidates`. Численные пороги фиксируются после golden/unit
набора, а не копируются из одного текущего экрана без проверки.

## 7. UX

Единая карточка кандидата показывает:

- название, винодельню и effective geography;
- выпуск/винтаж или NV, если подтверждены;
- объём/формат, если известны;
- изображение;
- уровень/процент уверенности;
- `почему похоже` и `что проверить`;
- открыть карточку;
- добавить в погребок;
- `Это не оно`.

Quick mode не скрывает критический выбор выпуска при конфликте. Detailed mode
раскрывает дополнительные поля, но не использует другой matcher.

Добавление принимает `wine_id`, optional `wine_vintage_id`, snapshot года/NV,
optional product-code/volume и acquisition context. До полной интеграции
`wine_vintage_id` существующий `user_storage.vintage` сохраняется совместимо.

## 8. Несколько фотографий

Разделять:

1. captures для OCR/matching;
2. приватные evidence-фото заявки;
3. проверенную публичную галерею wine/release;
4. фото состояния будущего bottle instance.

В Сессии 2 контракт принимает `labelCaptures[]`. Первый экран может начинать с
одного front-снимка. После неуверенного результата предложить необязательное фото
контрэтикетки или штрихкода и дополнить текущий запрос, а не запускать независимый
matcher.

Полная публичная галерея не входит. Если сохраняются несколько evidence-фото,
использовать дочернюю draft-media сущность с role/source/sort/provenance; старый
`photo_url` оставить cover/fallback.

## 9. Аналитика и защита от повторов

Измерять:

- channel;
- `exact/candidates/no_match/conflict/error`;
- количество кандидатов;
- обезличенные сигналы top candidate;
- выбранный candidate id;
- `Это не оно`;
- переход в draft;
- добавление в погребок;
- duplicate request/action suppression.

Каждый lookup получает request id. Кнопки add/reject защищаются от повторного
тапа. Повторное событие одного исхода в рамках request id не отправляется.

## 10. Не входит

- AI, Cloud.ru, Yandex Search и внешние search API;
- полная реализация Cellar Pro locations/stock lots;
- bottle instances, внутренние QR/NFC и инвентаризация;
- публичная медиагалерея;
- автоматическая публикация пользовательских кодов, выпусков и фото;
- автоматическое слияние конфликтующих wine;
- paywall и платежи.

## 10.1. Следующий этап: пользовательские предложения релизов

Каталог не должен зависеть только от ручного ввода администратора. Пользователь,
особенно коллекционер, может обладать более точными данными о собственной
бутылке и должен иметь возможность предложить отсутствующий релиз, фотографии и
товарный код прямо из сценария добавления в погреб.

При этом пользовательское предложение не публикуется автоматически в
каноническом каталоге. Рекомендуемый жизненный цикл:

```text
private draft -> submitted/pending -> verified
                            |-> needs_changes
                            |-> duplicate/merged
                            |-> rejected
                            |-> conflicted
```

До модерации пользователь может:

- сохранить бутылку в собственном погребе с приватным snapshot года/NV,
  фотографии и введённых характеристик;
- дополнять своё предложение и отвечать на запрос модератора;
- видеть, что данные ещё не подтверждены WinePool.

До статуса `verified` предложение:

- не становится каноническим релизом для остальных пользователей;
- не участвует как однозначный `exact` результат общего поиска по штрихкоду;
- не изменяет существующую карточку вина и подтверждённые релизы;
- может использоваться для поиска дублей и объединения одинаковых заявок на
  стороне модерации.

Чтобы не перенести бесконечную ручную работу на модераторов, очередь должна:

- автоматически искать возможный дубль вина, релиза, года/NV и товарного кода до
  отправки;
- предлагать пользователю дополнить существующий pending-релиз вместо создания
  нового;
- объединять голоса и доказательства нескольких пользователей в одну заявку;
- показывать модератору diff, источник каждого поля и фотографии, а не требовать
  повторного ручного ввода;
- позволять массово подтверждать независимые поля и связывать дубль с уже
  существующим релизом;
- учитывать историю качества вкладов пользователя для приоритета очереди, но не
  давать автоматическую публикацию только на основании рейтинга автора.

Минимальные данные предложения: базовое вино, винтаж или явный `NV`, название
релиза при наличии, фото лицевой и/или контрэтикетки, штрихкод, объём, рынок,
комментарий пользователя и provenance. Для спорных полей должны сохраняться
исходные evidence-фото и история модерационного решения.

Это отдельный подэтап после текущего административного вертикального среза. Он
должен переиспользовать существующие draft/moderation-механизмы и matcher, а не
создавать параллельный каталог или второй алгоритм поиска.

## 11. Порядок реализации

1. Проверить production-compatible фактическую схему и текущие дубли barcode.
2. Добавить миграцию `wine_vintages` и `wine_product_codes`, RLS/RPC/indexes и
   идемпотентный legacy перенос.
3. Добавить Dart domain/repository read contract и тесты.
4. Выделить единый matcher-фасад над receipt matcher.
5. Подключить barcode, label и text по одному.
6. Унифицировать candidate UI и действия.
7. Добавить quick/detailed presentation preference без роли пользователя.
8. Расширить аналитику и idempotency guards.
9. Выполнить узкие тесты и статический анализ без полной сборки.
10. Подготовить миграционный runbook, ручной QA и отдельный коммит.

## 12. Критерии приёмки

- три канала возвращают единый результат и используют существующий matcher;
- ни один путь не вызывает платный AI;
- несколько кодов одного wine/release поддерживаются;
- разные выпуски могут иметь разные коды;
- barcode conflict не выбирает случайную первую запись;
- legacy `wines.barcode` продолжает находиться;
- `NV` не смешивается с неизвестным годом;
- найденный выпуск добавляется в погребок с корректным vintage snapshot;
- quick mode остаётся коротким, detailed mode использует тот же контракт;
- ошибочный кандидат отклоняется и переходит в существующую модерацию;
- сырые OCR/поисковые данные не попадают в аналитику;
- подготовлены unit/migration tests, QA-чеклист и отдельный handoff.

### 13.13. Первый discovery-срез глобального поиска — 23.07.2026

- глобальный `/search` показывает рядом с текстовой строкой равноправные действия
  `Штрихкод` и `Этикетка`;
- оба действия переиспользуют существующие barcode/label routes и matcher, но
  передают явный `intent=discover`; отдельный поисковый алгоритм не создан;
- в discovery intent однозначный barcode сначала показывает найденный wine/release,
  а не открывает форму добавления в погреб автоматически;
- для discovery-кандидата `Открыть карточку` является primary CTA, а
  `Добавить в погреб` — secondary CTA; add-bottle intent сохраняет обратный
  приоритет;
- открытие кандидата загружает полную каноническую карточку через
  `WinesRepository.fetchWine`, поэтому описание, характеристики и отзывы не
  зависят от облегчённого search payload;
- high-confidence label в discovery intent остаётся на экране результата и не
  запускает подтверждение добавления автоматически;
- barcode no-match предлагает явное `Предложить добавить в каталог`, не создавая
  draft без действия пользователя;
- добавлены RU/EN строки; BE/UZ используют действующий fallback локализации;
- статический анализ затронутых маршрутов, экранов и общей карточки кандидата
  прошёл без замечаний.

### 13.14. Известный баг hardening: навигация «Редактировать вино» — 24.07.2026

- из меню «⋮» карточки вина (в т.ч. после модерации) действие «Редактировать вино»

## 14. Аудит незавершённости — 23.07.2026

### 14.1. Что действительно завершено

- реализован один application-фасад `CatalogFastSearchService` и общий контракт
  `CatalogSearchInput/Candidate/Result`;
- text, barcode и label внутри add-bottle используют общую outcome-policy;
- пороги ranked policy зафиксированы в коде: exact `0.85`, минимальный отрыв
  `0.12`, candidate `0.40`;
- barcode lookup различает однозначный exact и конфликт, не выбирая случайную
  первую запись;
- общая карточка кандидата показывает причины совпадения и ведёт в один confirm
  flow;
- additive-модель выпусков, кодов, фотографий и связи с погребом применена на
  production;
- quick/detailed переключатель минимально реализован в confirm sheet и хранится
  локально;
- базовые события результата, выбора, отказа, draft и добавления в погреб есть;
- пользовательское предложение релиза, уточнение, галерея, история и модерация
  реализованы и прошли production transaction QA.

### 14.2. Ключевое продуктовое несоответствие

Технически унифицирован matcher, но не пользовательская точка входа. Текущий
текстовый поиск воспринимается как способ изучения каталога, тогда как barcode и
label находятся прежде всего в `Добавить бутылку` и ведут к подтверждению
добавления. Новый пользователь, желающий только найти бутылку, прочитать описание,
оценки и отзывы, не видит единого поиска по трём каналам.

Поэтому формулировка `единый бесплатный поиск реализован` до закрытия раздела 15
запрещена. Корректная формулировка текущего состояния:

> Единый технический фасад поиска вина по тексту, штрихкоду и этикетке
> реализован. Единая discovery-точка входа и законченный пользовательский путь
> поиска и изучения вина не реализованы.

### 14.3. Другие незакрытые требования

- analytics events не содержат `request_id`, поэтому поиск, кандидаты и итоговое
  действие нельзя надёжно объединить в одну воронку;
- отсутствует общий request/action deduplication contract;
- нет зафиксированной сквозной QA-матрицы для всех исходов трёх каналов;
- quick/detailed существует только как локальное раскрытие полей confirm sheet,
  но не как объяснённая настройка и контекстная рекомендация;
- одинаковые pending-релизы разных пользователей не агрегируются;
- модератор не видит полноценный field-level diff с evidence конкретного поля;
- качество прошлых вкладов не влияет на приоритет очереди;
- итоговый handoff Сессии 2 и отдельный release record не подготовлены.

## 15. Обязательный продуктовый срез: единый discovery-поиск

### 15.1. Два намерения, один matcher

```text
Найти и изучить вино
  -> text | barcode | label
  -> единый wine result
  -> открыть карточку
  -> optional: добавить в погреб

Добавить бутылку
  -> тот же text | barcode | label matcher
  -> единый wine result
  -> подтвердить release/acquisition
  -> добавить в погреб
  -> optional: открыть карточку
```

Нельзя создавать отдельный discovery matcher. Различаются entry intent,
приоритет CTA и post-result navigation.

### 15.2. Единая точка входа

На глобальном экране поиска и в доступных с главной/каталога точках должны быть:

- текстовая строка;
- действие `Сканировать штрихкод`;
- действие `Сфотографировать этикетку`;
- понятное объяснение, что все три действия ищут существующее вино в каталоге.

Текстовый поиск сохраняет текущую широту: вина, винодельни, сорта и другие
каталожные сущности. Унифицируется wine-result; barcode и label остаются
wine-only каналами.

### 15.3. Единый результат

Для wine-кандидата независимо от канала показывать:

- название, винодельню, effective geography и изображение;
- подтверждённый release/vintage/NV, объём и формат при наличии;
- уверенность, `Почему похоже` и `Что проверить`;
- оценки, количество отзывов или явный переход к ним;
- primary CTA `Открыть карточку` для discovery intent;
- secondary CTA `Добавить в погреб`;
- `Это не оно` без принуждения к созданию заявки.

При add intent приоритет двух CTA меняется, но сама карточка и candidate contract
остаются общими.

### 15.4. Исходы

- однозначный barcode не должен молча добавлять бутылку: сначала показать краткий
  результат с конкретным релизом;
- conflict показывает все допустимые варианты и причину конфликта;
- label candidates позволяют дополнить тот же request контрэтикеткой или
  штрихкодом;
- no-match предлагает независимо `Предложить добавить в каталог` и
  `Добавить в личный погреб`;
- discovery, карточка и сканирование доступны гостю; регистрация требуется при
  персональном сохранении и отправке предложения.

### 15.5. Критерии приёмки discovery-среза

- новый пользователь находит три канала без перехода в `Добавить бутылку`;
- каждый канал может завершиться открытием полной карточки без записи в погреб;
- add-bottle продолжает работать на том же matcher;
- wine-result визуально и семантически одинаков для трёх каналов;
- широкий текстовый поиск виноделен/сортов не деградирует;
- no-match не запускает AI и не создаёт draft без явного действия;
- гостю не показывается registration wall до персонального действия.

## 16. Обязательное техническое завершение

### 16.1. Request analytics и idempotency

- передавать стабильный `request_id` во все события одного поиска;
- логировать channel, outcome, candidate count, обезличенные matched signals,
  selected candidate/rank, rejection, draft transition и cellar add;
- не передавать raw OCR и полный пользовательский текст;
- подавлять повтор одного outcome/action для одного `request_id`;
- защищать add/reject/propose от двойного тапа и повторной server-side записи;
- подготовить запрос/дашборд для долей `exact/candidates/no_match/conflict/error`.

### 16.2. Quick/detailed

- сохранить короткий quick flow;
- объяснить пользователю назначение detailed mode;
- предоставить настройку в профиле либо эквивалентную доступную настройку;
- контекстно предлагать detailed mode после работы с release, несколькими
  бутылками, форматом или местом хранения;
- не связывать preference с ролью `коллекционер` и не показывать её в onboarding;
- не смешивать UI preference с будущим Cellar Pro entitlement.

### 16.3. Масштабирование пользовательских предложений релизов

- искать активный pending-дубль по wine + vintage/NV + release identity + code
  независимо от автора;
- предлагать дополнить существующее предложение вместо создания параллельного;
- агрегировать независимые evidence и вклад нескольких пользователей без
  раскрытия их персональных данных друг другу;
- показывать модератору field-level diff, provenance и evidence каждого поля;
- позволять независимо подтвердить/отклонить безопасные поля и связать дубль с
  каноническим релизом;
- учитывать историю подтверждённых/отклонённых вкладов только для приоритета
  очереди, без автоматической публикации;
- сохранить полный audit trail объединения, решений и авторства evidence.

### 16.4. Тесты и QA

Обязательны unit/integration tests и ручная матрица:

- text: exact, candidates, no-match, hard mismatch;
- barcode: verified exact, legacy exact, conflict, pending-only, absent;
- label: front only, front+back, front+barcode, candidates, no-match;
- discovery: открыть карточку без добавления;
- add: корректные `wine_vintage_id`, NV/unknown snapshot и release photo;
- rejection: `Это не оно` и явный переход в существующий draft-flow;
- guest: поиск доступен, персональное действие требует вход;
- duplicate taps/requests не создают повторных записей и событий;
- ни один бесплатный путь не вызывает пользовательский Copilot или внешний
  search API.
