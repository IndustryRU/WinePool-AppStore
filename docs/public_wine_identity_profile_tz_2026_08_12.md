## 2. Цели

### Для пользователя

- красиво представить себя винному сообществу;
- объяснить контекст своих отзывов и рекомендаций;
- показать интересы, опыт, профессиональную роль и винные путешествия;
- самостоятельно управлять публичностью каждого чувствительного блока;
- видеть профиль именно так, как его увидят другие.

### Для WinePool

- повысить доверие к пользовательским отзывам и вкладу в каталог;
- сформировать основу социальных связей без преждевременного запуска соцсети;
- связать отзывы, вклад, экспертный и туристический контуры одним автором;
- не допустить самовольного присвоения подтверждённых профессиональных регалий.

## 3. Продуктовые принципы

1. Заполнение добровольное. Пустые секции публично не показываются.
2. Email, телефон, legal/admin данные никогда не попадают в публичный read model.
3. `Эксперт WinePool` — системный уровень за вклад, а не профессия.
4. `Сомелье`, `винный гид` и иные роли могут быть указаны пользователем, но подтверждение отображается отдельно.
5. Владелец видит предпросмотр даже при закрытом профиле; остальные — только опубликованные данные.
6. Публичность включается осознанно и не активируется миграцией для старых аккаунтов.
7. Туристическая статистика считается только по подтверждённым событиям WinePool; желания и самоописание маркируются отдельно.
8. Универсальная визитка не заменяет `expert_profiles`: экспертный профиль остаётся capability/business-слоем консультаций.

## 4. UX в текущем профиле

### 4.1. Действия шапки

- тап по значку камеры на аватаре — заменить фотографию;
- тап по карандашу — открыть редактор винной визитки (имя входит в редактор);
- тап по основной области шапки (аватар вне камеры, имя, центральная область) — открыть полноэкранный предпросмотр;
- email остаётся только в приватной шапке настроек и не показывается в визитке.

Зоны нажатия не должны конфликтовать. Камера и карандаш перехватывают собственные события, остальная карточка открывает preview.

### 4.2. Предпросмотр владельца

Экран визуально совпадает с публичным профилем. Владелец дополнительно видит:

- метку `Так ваш профиль видят другие`;
- статус `Не опубликован`, если публичность выключена;
- прогресс заполнения;
- пустые секции как аккуратные предложения заполнить (они не видны другим);
- кнопку `Редактировать профиль`;
- кнопку `Поделиться` только после публикации.

### 4.3. Публичный экран

Маршрут целевой модели: `/people/:userId` или `/u/:publicSlug`. MVP может использовать UUID внутри приложения, но публичную web-ссылку следует строить только после введения уникального slug.

Порядок секций:

1. Hero: крупная фотография, имя, город/страна при разрешении.
2. Уровень WinePool: уровень, локализованное звание, XP и прогресс.
3. Краткая подпись.
4. `Обо мне`.
5. Роль и винные интересы.
6. `Вклад в WinePool` — только серверные показатели.
7. `Путешествия`.
8. Подтверждённая квалификация и достижения.
9. Публичные ссылки.

На чужом профиле нет email, редактирования, внутренних статусов модерации и приватной статистики.

## 5. Поля визитки

### 5.1. Основное (MVP)

| Поле | Ограничение | Публичность |
|---|---:|---|
| `display_name` | 2–80 | вместе с профилем |
| `avatar_url` | текущее хранилище | вместе с профилем |
| `headline` | до 120 | отдельный флаг не нужен |
| `bio` | до 800 | секция `Обо мне` |
| `city`, `country_code` | справочник/текст | отдельный флаг |
| `primary_role_code` | управляемый справочник | отдельный флаг |
| `interest_codes` | до 12 | отдельный флаг |
| `website_url` | 1 URL | отдельный флаг |
| `is_public` | boolean | master switch |

Существующие `profiles.full_name`, `avatar_url`, `website`, `home_country` не дублировать. Расширенные поля лучше хранить в отдельной 1:1 таблице, чтобы публичная модель не раздувала auth profile.

### 5.2. Роли

Начальный управляемый набор:

- wine_enthusiast — любитель вина;
- collector — коллекционер;
- sommelier — сомелье;
- caviste — кавист;
- wine_expert — винный эксперт;
- winemaker — винодел;
- winery_representative — представитель винодельни;
- wine_guide — винный гид / экскурсовод;
- tour_organizer — организатор винных путешествий;
- author_journalist — автор / журналист;
- educator — преподаватель / школа;
- other — другое (текст проходит модерацию).

В MVP выбирается одна основная роль. Архитектура допускает несколько ролей позже.

Отображение роли:

- `Указано пользователем` — нейтрально, без галочки;
- `На подтверждении` — только владельцу;
- `Подтверждено WinePool` — публичная отметка;
- `Отклонено/нужны сведения` — только владельцу и модератору.

### 5.3. Интересы

Управляемые локализуемые коды, а не произвольные строки. Стартовый набор:

- российское вино;
- автохтонные сорта;
- игристые;
- тихие вина;
- натуральные вина;
- коллекционирование;
- слепые дегустации;
- гастрономические сочетания;
- винные фестивали;
- винодельни и терруары;
- винный туризм;
- история и культура вина.

Регионы и страны не смешивать с интересами: для них позже нужен отдельный справочник любимых регионов.

## 6. Раздел «Путешествия»

Раздел необязательный и пустым не показывается.

### MVP

- `travel_intro` до 500 символов;
- туристическая роль (путешественник, гид, организатор);
- туристические интересы-чипы;
- любимые винные регионы (до 10, первоначально управляемый текст/справочник);
- `show_travel_section`.

### Следующий этап

- количество подтверждённо посещённых виноделен;
- страны и регионы;
- карта посещений;
- последние поездки / карточки памяти;
- публичные маршруты и заметки.

Источники данных маркируются:

- `По данным WinePool` — check-in, завершённая заявка/тур с подтверждением, другой anti-fraud event;
- `Указано пользователем` — текст и любимые регионы.

Сканирование чека рядом с винодельней, просмотр карточки, построение маршрута или заявка без подтверждения не считаются посещением. Публичный факт посещения требует согласия пользователя согласно tourism ТЗ.

## 7. Профессиональные сведения и квалификация

Не входят в первый технический срез, но схема должна их поддерживать.

Сущность `user_profile_credentials`:

- `id`, `user_id`;
- `credential_type`;
- `title`, `organization`, `year`;
- `description`;
- `evidence_url` (private storage);
- `public_source_url`;
- `verification_status`;
- `moderator_id`, `moderated_at`, `decision_note`;
- `is_public`;
- timestamps.

Документы хранятся приватно и доступны только владельцу и уполномоченному модератору. Публично выводятся только утверждённые поля, но не сам документ, если пользователь отдельно не разрешил ссылку.

Связь с `expert_profiles`:

- универсальная визитка показывает личность, опыт и вклад;
- approved `expert_profiles` добавляет capability `Принимает консультационные запросы`, услуги и профессиональную карточку;
- подтверждённые credentials могут использоваться при модерации expert profile, но не создают его автоматически.

## 8. Вклад и системный уровень

Источник — существующая серверная статистика вклада/XP. Клиент не сохраняет вычисленные числа в публичной анкете.

Показывать:

- уровень и локализованное звание;
- XP;
- чеки;
- добавленные вина;
- подтверждённые исправления/релизы/фото (по мере доступности read model);
- отзывы, если они публичны.

Нужен единый RPC/read model, чтобы чужой профиль не мог прочитать приватные события начисления XP. Публичны агрегаты, но не audit log.

## 9. Предлагаемая модель данных

### 9.1. `user_public_profiles` (1:1)

```sql
user_id uuid primary key references profiles(id) on delete cascade
public_slug text unique null
headline text null
bio text null
city text null
country_code text null
primary_role_code text null
role_verification_status text not null default 'self_declared'
interest_codes text[] not null default '{}'
travel_intro text null
travel_role_code text null
travel_interest_codes text[] not null default '{}'
favorite_region_codes text[] not null default '{}'
is_public boolean not null default false
show_location boolean not null default false
show_role boolean not null default true
show_interests boolean not null default true
show_contribution boolean not null default true
show_travel_section boolean not null default false
show_credentials boolean not null default false
published_at timestamptz null
created_at timestamptz not null
updated_at timestamptz not null
```

Имя, аватар, website читаются из `profiles` только через безопасный view/RPC.

### 9.2. Справочники

Рекомендуется использовать существующий управляемый Atlas/knowledge подход либо отдельные небольшие таблицы `profile_role_terms`, `profile_interest_terms`, `wine_region_terms`. UI хранит стабильный code; локализованная подпись приходит из ARB на MVP или справочника позже.

### 9.3. RPC/read models

- `get_my_public_profile_editor()` — все собственные поля и статусы;
- `save_my_public_profile(...)` — серверная валидация длины, URL и кодов;
- `publish_my_public_profile()` / `unpublish_my_public_profile()`;
- `get_public_user_profile(p_user_id|p_slug)` — только разрешённые поля и агрегаты;
- `get_public_user_profile_contribution(...)` можно объединить с предыдущим RPC;
- moderation RPC для роли/credentials во второй фазе.

## 10. RLS и приватность

- владелец читает и редактирует свою полную запись;
- anon/authenticated читают только `is_public = true` через ограниченный view/RPC;
- прямой public select из `profiles` не расширять;
- email и auth metadata отсутствуют в возвращаемом типе;
- moderator читает заявки на верификацию только при capability;
- evidence bucket private, signed URL выдаётся владельцу/модератору;
- удаление аккаунта каскадно удаляет визитку и credentials;
- выключение публичности немедленно исключает профиль из public RPC;
- блокировка/модерационное скрытие имеет серверный приоритет над `is_public`.

Нужны поля `moderation_status`/`visibility_override` либо отдельная moderation table, если свободные тексты будут публичны без премодерации. Рекомендуемый MVP: bio публикуется сразу, но доступна жалоба и административное скрытие; профессиональная верификация — только после модерации.

## 11. Редактор

Пошаговая форма без обязательного полного заполнения:

1. `Основное`: имя, фото, headline, город.
2. `Обо мне`: bio, основная роль.
3. `Интересы`: чипы.
4. `Путешествия`: выключенная по умолчанию секция.
5. `Публичность`: preview и переключатели.

Автосохранение не требуется в MVP. Перед выходом с изменениями — подтверждение. Кнопки: `Предпросмотр`, `Сохранить`, `Опубликовать/Снять с публикации`.

Валидация выполняется и на клиенте, и в RPC. Запрещены пустые URL, управляющие символы и чрезмерные переносы. Ссылки открываются внешне и проходят allowlist схем `https`.

## 12. Точки входа

MVP:

- шапка собственного профиля;
- аватар/имя автора публичного отзыва;
- аватар/имя автора подтверждённого вклада на главной.

Позже:

- каталог экспертов;
- туристические check-in/маршруты;
- рейтинги и комментарии;
- поиск пользователей и подписки (отдельное продуктовое решение).

Если профиль закрыт, тап автора может показывать компактную системную карточку: имя, аватар, уровень и публичный вклад, если политика это разрешает. Рекомендуемое решение: имя/аватар уже публичны в отзыве, но расширенный экран открывается только при `is_public`.

## 13. Модерация и жалобы

MVP:

- административно скрыть весь профиль;
- скрыть bio/headline;
- журнал причины и moderator id;
- пользователь может исправить и повторно опубликовать только после снятия блокировки;
- кнопка жалобы на публичном профиле, если общий complaint-контур готов.

Фаза 2:

- очередь ролей и credentials;
- запрос дополнительных доказательств;
- approved/rejected/revision_requested;
- уведомления пользователю;
- audit trail без удаления решений.

## 14. Мотивация заполнения

- карточка `Создайте винную визитку` в собственном профиле;
- процент заполнения только владельцу;
- contextual prompts после первого публичного отзыва или существенного вклада;
- без регулярного XP за текстовые поля;
- допустим одноразовый achievement за опубликованную содержательную визитку, но не денежная/XP гонка;
- пустой или формальный текст не должен давать награду.

## 15. Локализация и доступность

- все роли, интересы, статусы и copy — через ARB (`ru`, `en`, `be`, `uz`);
- корректные plural формы статистики;
- dynamic text scale без обрезания;
- семантические подписи для аватара, уровня и verification badge;
- контраст золотых чипов на тёмном фоне;
- hero-фото имеет fallback и не является единственным носителем смысла;
- web/mobile responsive: одна колонка на телефоне, hero + summary grid на широком экране.

## 16. Аналитика

События без текста bio и персональных данных:

- `public_profile_preview_opened`;
- `public_profile_edit_started`;
- `public_profile_saved` (filled section codes);
- `public_profile_published` / `unpublished`;
- `public_profile_viewed` (source: review/home/expert/tourism/share);
- `public_profile_share_clicked`;
- `profile_travel_section_enabled`;
- `profile_role_verification_started/completed`;
- `public_profile_reported`.

Метрики: доля опубликованных профилей, завершение редактора, просмотры после отзывов, влияние заполненного профиля на открытие отзывов. Не отправлять свободный текст в AppMetrica.

## 17. Совместимость и миграция

- additive migration, текущие поля `profiles` не переименовывать;
- существующие клиенты 1.0.6/1.1.0 продолжают читать прежний `Profile`;
- отсутствие строки `user_public_profiles` эквивалентно закрытой пустой визитке;
- старые RPC отзывов не менять разрушительно;
- новые public fields добавлять через новые versioned RPC/views;
- до удаления legacy-path выдержать минимум один релиз совместимости.

## 18. Этапы реализации

### Phase 0 — решения и прототип

- подтвердить набор MVP-полей и ролей;
- визуальный прототип preview/editor;
- аудит текущих публичных мест с автором;
- threat/privacy review.

### Phase 0.5 — Profile Light в текущем релизе

Цель — дать пользователю аккуратную расширенную визитку уже сейчас, но не вносить в
текущий релиз социальный, экспертный и туристический контуры целиком.

В light-версию входят:

- тап по центральной области шапки собственного профиля открывает полноэкранный
  preview; действия камеры и карандаша остаются независимыми;
- в hero используются уже существующие avatar, имя, уровень WinePool и XP;
- один короткий headline (например, `Любитель российских вин`);
- одно поле `О себе` с небольшим лимитом;
- одна основная роль из контролируемого списка, явно помеченная как указанная
  пользователем, а не подтверждённая WinePool;
- несколько контролируемых интересов-чипов, включая винный туризм;
- редактирование и preview владельца;
- additive-хранилище, совместимое с будущей полной схемой;
- локализация RU/EN/BE/UZ, состояния loading/error/empty и базовая аналитика без
  передачи текста.

В light-версию **не входят**:

- публичный каталог людей, поиск пользователей, подписки и личные сообщения;
- публичный web URL/slug и кнопка share;
- квалификации, загрузка дипломов, verification badge и экспертные заявки;
- карта путешествий, check-in, посещённые регионы и туристическая статистика;
- отдельные секционные privacy-настройки: до полной версии действует один master
  switch; если публичные точки входа текущего релиза не подключены, он хранится
  выключенным и не показывается как обещание пользователю;
- новые XP-награды за заполнение текста;
- обязательное заполнение или новый шаг онбординга.

Архитектурное правило: light — это первый срез `user_public_profiles`, а не временные
поля в `profiles` и не отдельная одноразовая форма. Поля, RPC и Flutter-модели должны
без переноса данных расширяться в Phase 1. Если миграция и RLS не проходят полный
регрессионный цикл до freeze текущего релиза, Profile Light целиком переносится в
следующий патч/feature-релиз, а не выпускается частично.

### Phase 1 — MVP визитки

- additive schema + RLS + RPC;
- preview владельца;
- редактор основных данных, bio, роли, интересов;
- master public switch и секционные настройки;
- публичный экран;
- переход из публичного отзыва;
- локализация и аналитика.

### Phase 2 — туризм

- travel intro/interests/regions;
- подтверждённые check-in агрегаты;
- карта и visit memory cards;
- granular privacy.

### Phase 3 — квалификация и эксперты

- credentials + private evidence;
- moderation/admin UI;
- verification badges;
- связь с `expert_profiles` и консультациями.

### Phase 4 — социальный слой (отдельное подтверждение)

- подписки;
- поиск людей;
- рекомендации авторов;
- публичные коллекции/маршруты;
- блокировка пользователей и расширенная complaint safety.

## 19. Acceptance criteria MVP

1. Тап по центральной области собственной шапки открывает preview; камера и карандаш сохраняют отдельные действия.
2. В preview нет email; отображение совпадает с чужим публичным экраном.
3. Старый пользователь без новой записи работает без ошибок и остаётся непубличным.
4. Пользователь может заполнить, сохранить, опубликовать и снять визитку с публикации.
5. Чужой пользователь получает только разрешённые поля через серверный read model.
6. Уровень WinePool визуально отделён от self-declared/verified роли.
7. Пустые секции не видны другим.
8. Туристическая секция по умолчанию выключена.
9. Email, evidence и moderation notes невозможно получить public/anon запросом.
10. Профиль доступен с автора отзыва, если опубликован.
11. RU/EN/BE/UZ сгенерированы без untranslated messages.
12. Старые версии приложения и старые RPC не ломаются.

### Acceptance criteria Profile Light

1. Пустой light-профиль не меняет внешний вид существующего профиля и не заставляет
   пользователя что-либо заполнять.
2. Тап по центральной области шапки открывает preview; camera/pencil сохраняют прежние
   действия.
3. В preview отсутствует email и любая служебная информация.
4. Headline, bio, основная роль и интересы сохраняются после перезапуска приложения.
5. Роль визуально не выглядит подтверждённой профессиональной квалификацией.
6. Старые клиенты 1.0.6 и 1.1.0 продолжают работать с таблицей `profiles` и прежними RPC.
7. Ошибка чтения новой таблицы не блокирует открытие обычного профиля.
8. Все новые строки локализованы, длинный текст и text scale не ломают экран.
9. В релизе нет неработающих входов в путешествия, экспертов, sharing или публичный
   каталог людей.

## 20. QA-матрица

- новый/старый аккаунт;
- пустой, частично заполненный, полный профиль;
- public on/off;
- каждый секционный privacy flag;
- владелец/другой auth/guest/moderator;
- заблокированный профиль;
- удалённый avatar и битая ссылка;
- длинное имя, headline, bio, RTL-like/Unicode input;
- text scale 1.0/1.3/1.6;
- Android узкий экран, планшет, web;
- переход из отзыва и back navigation;
- offline/error/retry;
- RLS negative tests на email/evidence;
- совместимость 1.0.6 и текущей release-ветки.

## 21. Решения, требующие продуктового подтверждения

Рекомендации по умолчанию:

1. Публикация bio без премодерации, но с жалобой и admin hide — **рекомендуется**.
2. Основная роль self-declared; галочка только после проверки — **рекомендуется**.
3. Город показывать выключенным по умолчанию — **рекомендуется**.
4. Системные агрегаты вклада показывать включёнными при публикации, с возможностью скрыть — **рекомендуется**.
5. Публичный slug отложить до web/share-фазы; внутри приложения использовать user id — **рекомендуется**.
6. Один основной role в MVP — **рекомендуется**.
7. Туризм в первом MVP только как текст/интересы, автоматическую карту вынести в Phase 2 — **рекомендуется**.
8. Не вводить подписки и личные сообщения вместе с визиткой — **рекомендуется**.

## 22. Рекомендуемый первый технический срез

### 22.1. Текущий релиз: безопасный light-срез

1. additive migration с минимальным подмножеством `user_public_profiles`;
2. own read/save RPC + RLS tests;
3. модель/repository/provider с graceful fallback;
4. полноэкранный preview владельца;
5. редактор headline, bio, одной роли и интересов;
6. локализация, аналитика и responsive QA;
7. регрессия профиля и совместимости 1.0.6/1.1.0.

Не включать пункт в релиз, если до release freeze не завершены migration/RLS/compatibility
tests. В таком случае переносится весь light-срез без промежуточной UI-заглушки.

### 22.2. Отдельный следующий feature-релиз: полная визитка

1. миграция `user_public_profiles`;
2. расширение own editor/public read RPC и RLS tests;
3. модель/repository/provider;
4. расширение preview владельца;
5. редактор: город, секционная приватность и public switch;
6. публичный экран и переход из отзыва;
7. аналитика, локализация, responsive QA;
8. документация и production migration runbook.
