# WinePool — стартовый промпт Session 2.5

Дата фиксации: 29.07.2026

Назначение: передать в отдельную задачу Codex реализацию Session 2.5 — релизный
опыт, политика фотографий и обновлённая карточка вина. Session 2 функционально
закрыта коммитом `61e17bae`; release-решение закреплено коммитом `7914d6fc`.

## Готовый промпт

```text
Продолжаем WinePool в репозитории R:\Flutter\Project\winepool_final.

Нужно выполнить отдельную Session 2.5: «Релизный опыт, фотографии релизов и
карточка вина». Это самостоятельная подсессия между завершённой Session 2 и
Session 2.6. Пользовательский Copilot/Session 3 в эту задачу не входит.

Сначала полностью прочитай и сопоставь:
1. docs/catalog_search_copilot_four_session_execution_plan_2026_07_17.md;
2. docs/catalog_fast_search_session2_handoff_2026_07_25.md;
3. docs/catalog_fast_search_session_2_tz_2026_07_18.md;
4. docs/release_experience_and_wine_card_roadmap_2026_07_24.md;
5. docs/catalog_fast_search_session2_qa_matrix_2026_07_25.md;
6. docs/session_2_5_release_experience_start_prompt_2026_07_29.md.

Проверь актуальное дерево Git и все коммиты после `61e17bae` и `7914d6fc`.
Сохраняй любые несвязанные пользовательские изменения. Не считай документацию
доказательством фактического состояния: сверь код, миграции и production-схему.

Цель Session 2.5

Сделать релизы/винтажи полноценной публичной частью поиска и карточки вина,
сохранив премиальный вид WinePool и существующие безопасные moderation-flow.

Обязательный объём

A. Аудит перед реализацией
- Найди все пользовательские и административные поверхности карточки вина,
  результатов текстового/GTIN/label-поиска и добавления в погреб.
- Проаудируй `wine_vintages`, `wine_vintage_images`, `wine_product_codes`, модели,
  RPC, repositories, кеширование, маршруты и права гостя/пользователя/модератора.
- Составь таблицу «поле заполнено в БД → где читается → где показывается → что
  нужно изменить». Обязательно проверь `release_name`, год/NV, `alcohol_level`,
  `grape_composition`, `characteristics`, роли фотографий, объёмы/GTIN,
  effective-географию, `is_pet_nat`, `is_organic`, `is_biodynamic`, `is_natural`,
  температуру подачи, вкусовой профиль (`null` не равен 0), рейтинги и отзывы.
- Перед кодом дай краткий evidence-backed отчёт, план и перечисли решения, которые
  действительно требуют подтверждения владельца. Не создавай новый параллельный
  источник релизов или matcher.

B. Decision record по изображениям — выполнить первым
- Формально закрепи различие showcase-фото и evidence-фото релиза.
- Рекомендуемая политика hero: showcase выбранного релиза → showcase другого
  релиза этого вина → `wines.image_url` → премиальный placeholder.
- Непроверенное пользовательское evidence-фото не может автоматически стать
  публичным hero.
- Сохрани существующие роли: лицевая этикетка, контрэтикетка, штрихкод, бутылка
  целиком и другое. Не теряй provenance, автора, primary и sort order.
- Реши additive-способ хранения showcase-качества. До изменения схемы проверь,
  нельзя ли безопасно переиспользовать существующие поля. Не делай массовый
  backfill без отдельного обоснования.
- Per-volume/SKU-фото не нужно насильно завершать в 2.5: подготовь расширяемый
  контракт, а объёмную коммерческую привязку оставь Session 2.6.

C. Релизы в поиске
- В текстовом, GTIN- и label-поиске показывай доступные релизы одного вина
  компактно: год/NV, релизное фото и релевантные признаки.
- Если exact GTIN соответствует нескольким релизам одного вина, это не конфликт:
  покажи варианты и попроси выбрать год/NV; оставь «Не знаю год» и
  «Нет нужного релиза».
- Распознанный OCR-год должен поднимать подходящий релиз, но не выбирать его
  необратимо без возможности сменить.
- Выбор релиза должен передавать корректный `wine_vintage_id` дальше в карточку и
  существующий add-bottle flow. Не допускай молчаливого добавления в погреб.
- «Нет моего релиза — предложить» переиспользует существующую очередь модерации,
  галерею и multi-contributor механизм Session 2.

D. Карточка вина
- Перестрой карточку вокруг сущностей Wine → Release/Vintage → SKU/GTIN, но не
  смешивай общие свойства вина с релизными.
- Добавь понятный селектор релиза. Невыбранное состояние показывает wine-level
  данные; выбранное — фото, год/NV, название выпуска, алкоголь, состав и отличия
  конкретного релиза.
- Смена релиза должна быть обратимой и сохранять стабильную навигацию.
- Покажи полезные уже заполненные данные из аудита, не превращая карточку в
  административную анкету. Применяй progressive disclosure.
- Гостю разрешён просмотр карточки и релизов. Авторизация требуется только для
  персонального сохранения, предложения данных и других изменяющих действий.
- Модераторские действия через «⋮» и маршруты редактирования должны сохраниться.
- Обязательно проверь адаптивность Android/iOS/web, длинные названия, отсутствие
  фото, один релиз, много релизов, NV, архивные релизы и неполные данные.

E. Границы
- Не реализуй пользовательский AI/Copilot и не вызывай внешние search API.
- Не начинай Session 2.6 и не переводь `offers` на новую схему в этой задаче.
- Не добавляй платёжный контур, полный Cellar Pro, автопубликацию пользовательских
  материалов или публичный показ evidence-фото без модерации.
- Не ломай существующие text/GTIN/label discovery, add-bottle, идемпотентность,
  multi-contributor moderation и сохранение vintage snapshot.

F. Миграции и production
- Все изменения БД только additive и обратно совместимые.
- Перед production-миграцией: полный backup, SHA-256, dry-run BEGIN/ROLLBACK,
  затем apply и post-check. Запиши команды, результат и путь backup в handoff.
- Не удаляй legacy-поля и не выполняй необратимый массовый backfill.
- Admin web после готовности можно собирать и деплоить без дополнительного
  согласования. APK/AAB/IPA не собирай: Android APK собирает владелец, а store
  artifacts готовятся только после Session 2.6 для версии 1.1.0.

G. Проверка и приёмка
- Добавь unit/widget/integration-тесты для resolver изображений, выбора релиза,
  fallback-цепочки, `null`-семантики и передачи `wine_vintage_id`.
- Повтори профильные тесты Session 2 и убедись, что бесплатные пути не вызывают
  Copilot/внешний search.
- Проведи targeted analyze изменённых файлов. Полный analyze оценивай относительно
  существующего baseline и не исправляй несвязанные старые проблемы.
- Подготовь отдельную подробную ручную QA-матрицу Session 2.5: поиск тремя
  способами, карточка без/с одним/несколькими релизами, NV, фото/fallback,
  гость/пользователь/модератор, add-bottle, предложение отсутствующего релиза,
  Android/iOS/web и регрессии Session 2.

H. Документация и завершение
- Создай отдельные Session 2.5 ТЗ, QA-матрицу и handoff либо явно обнови
  существующий roadmap со ссылками на них.
- Зафиксируй decision record изображений, миграции/backups, коммиты, deploy,
  ограничения и отложенное для Session 2.6.
- Не объявляй Session 2.5 verified до ручной приёмки владельцем.
- После фактического завершения сделай отдельный коммит только относящихся к
  Session 2.5 файлов; не push без явной просьбы.

Начни с аудита и краткого плана. До реализации остановись только на тех решениях,
которые действительно меняют продуктовую политику или необратимо влияют на схему.
Во всех остальных безопасных и обратимых шагах продолжай самостоятельно.
```
