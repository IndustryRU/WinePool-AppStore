## 1. Проблема

Когда пользователь сканирует чеки, магазины подтягиваются автоматически (`user_receipts.shop_name`, `shop_address`, `lat`, `lng`). Но:

1. Название в чеке — часто **юридическое лицо** (`ООО "Альфа-Трейд"`), а не вывеска, которую человек видит (`Пятёрочка`, `Красное & Белое`, `ВкусВилл`). Пользователь не узнаёт свой магазин.
2. Нет единого места, где пользователь видит **список своих магазинов** и может ими управлять.
3. При **ручном** добавлении вина (без чека) пользователю негде быстро выбрать «где купил» — он печатает руками. А покупает он обычно в 2-3 привычных местах.

Цель: дать пользователю личную базу мест из его же чеков, с человеческим названием по его выбору, переиспользуемую везде, где есть «место покупки».

## 2. Что Уже Сделано (Лёгкий Пикер, 13.06.2026)

В ручном добавлении (`ManualDraftScreen`) поле «Где куплено» дополнено быстрыми чипами магазинов пользователя:

- источник: `ManualDraftRepository.fetchKnownShops()` — distinct по имени из `user_receipts`, самая свежая запись с гео;
- провайдер: `knownShopsProvider`;
- тап по чипу заполняет имя и переносит `address`/`lat`/`lng` в контекст бутылки (`ManualBottleParams`), пока имя в поле совпадает с выбранным магазином;
- модель: `KnownShop { name, address, lat, lng }`.

Этого достаточно для быстрого выбора, но НЕ покрывает: переименование (юр. → вывеска), отдельный раздел управления, единое использование во всех местах с местом покупки.

## 3. Целевой Функционал (Полный Слайс)

### 3.1. Раздел «Мои места»

Отдельный экран (например, route `/my-places`, вход из профиля и/или из карты покупок):

- список магазинов пользователя, агрегированный из чеков + ручных добавлений;
- по каждому месту: отображаемое имя (пользовательское, если задано, иначе из чека), адрес, количество покупок, мини-карта/иконка, число вин/сумма (опционально);
- действие «Переименовать» — задать своё название (вывеску), не меняя данные чека;
- действие «Объединить» — если одно место пришло под разными юр. написаниями, схлопнуть в одно (опционально, post-MVP внутри слайса);
- тап по месту → список вин/покупок в этом магазине (drill-down уже есть в map-experience: «Вина из магазина»).

### 3.2. Переименование (Ядро Слайса)

- пользовательское имя хранится отдельно от исходного `shop_name` из чека (raw сохраняется для аудита и матчинга, как в принципах нормализации каталога);
- переименование НЕ меняет `user_receipts` — это пользовательский alias поверх;
- отображаемое имя пользователя применяется везде: карта покупок, история чеков, ручное добавление, карточка вина «где покупали».

### 3.3. Использование Везде

Единый источник «отображаемое имя места» для:

- ручного добавления (пикер уже есть — переключить на пользовательские имена);
- карты покупок (`/my-wine-map`) и drill-down «Вина из магазина»;
- истории чеков (показывать вывеску вместо юр. лица, с возможностью увидеть оригинал);
- карточки вина «где покупали это вино» (для личных точек пользователя).

## 4. Модель Данных

Рекомендуемая таблица (на согласование при реализации):

`user_shop_places` (или `user_shop_aliases`):

- `id uuid pk`
- `user_id uuid not null`
- `normalized_source_name text not null` — нормализованное имя из чека (ключ матчинга)
- `display_name text not null` — пользовательское имя (вывеска)
- `canonical_address text null` — представительный адрес
- `lat double precision null`, `lng double precision null`
- `receipt_count int` (можно считать запросом, не хранить)
- `created_at`, `updated_at`
- уникальность по `(user_id, normalized_source_name)`

Принципы:

- raw `shop_name` из чека не теряется (остаётся в `user_receipts`);
- маппинг «нормализованное имя из чека → пользовательское имя» приватный, RLS user-scoped;
- агрегация мест — из `user_receipts` + manual `draft_wine_sources` (shop_name) + наложение `user_shop_places.display_name`.

Открытый вопрос: матчить место по имени, по адресу, или по (имя+адрес)? Сети (Пятёрочка) имеют много адресов под одним именем — решить, место это «бренд» или «конкретная точка». Рекомендация: на уровне MVP-слайса место = конкретная точка (имя+адрес/гео), а пользовательское имя применяется к бренду (всем точкам с тем же нормализованным именем) либо к конкретной точке — определить при реализации.

## 5. UX-Состояния

- пустой список (нет чеков и ручных мест) — объяснение, как появляются места;
- переименование — инлайн или bottom sheet, валидация непустого имени;
- сетевой сбой загрузки/сохранения — понятная ошибка, не теряем ввод;
- место без гео — карточка без карты, но переименование доступно.

## 6. Границы Слайса

Входит:

- раздел «Мои места», переименование, применение имени везде, где есть место покупки.

Не входит (отдельно/позже):

- публичные/общие места между пользователями (это другой governance-слой, как каталог);
- редактирование адреса/координат вручную (только пользовательское имя в MVP-слайсе);
- импорт мест извне.

## 7. Критерии Приёмки

- [ ] пользователь видит раздел «Мои места» со списком из своих чеков;
- [ ] пользователь может переименовать место (юр. → вывеска), не меняя данные чека;
- [ ] переименование отражается в ручном добавлении, карте покупок, истории чеков, карточке вина;
- [ ] ручное добавление использует пользовательские имена в пикере;
- [ ] raw `shop_name` из чека сохранён и доступен;
- [ ] RLS: пользователь видит только свои места;
- [ ] `flutter analyze` чистый; миграция применена по протоколу backup → review → apply.

## 8. Триггер Реализации

Начинать после завершения add-bottle проходов (проход 5) и стабилизации потока ручного добавления, либо раньше — если пользователи в обратной связи укажут на «не узнаю свои магазины» как на частую боль.

## 10. Обновление Пикера 10.08.2026

- Пикер показывает сопоставленный `retail_brands.name`; юридическое имя из
  чека остаётся fallback и сохраняется как техническая идентичность точки.
- Список сгруппирован по стране и городу: заголовок содержит флаг, город и
  количество точек, а раскрытая группа — бренды, адреса и даты покупок.
- Добавлена additive-функция `get_user_purchase_map_v2()`. Исходная
  `get_user_purchase_map()` сохранена без изменений для клиентов 1.0.6.
- Если бренд или страна ещё не сопоставлены, интерфейс корректно использует
  очищенное юридическое имя и группу «Город не определён».
- Заголовок города агрегирует количество магазинов и купленных бутылок;
  раскрытая карточка точки показывает собственное количество бутылок.
- Для будущей доработки карты сохранить этот список как второй режим просмотра
  тех же данных (карта по умолчанию + список точек). В релиз 1.1.0 отдельную
  переработку экрана карты не включать.
- Пикер использует отдельную additive-функцию
  `get_user_shop_picker_places_v1()`: одинаковые юридическое имя и координаты
  образуют одну точку, а покупка не считается повторно, если запись погребка
  уже связана с исходной строкой чека или ручным источником. Исторические RPC
  карты не изменяются.
