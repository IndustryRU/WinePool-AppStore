## 1. Зачем

Справочник знаний построен: 130 терминов Atlas с иерархией и синонимами,
карточка вина показывает факты чипами и умеет вести в статью. Издательской
части нет: **шесть статей зашиты в код**, у всех 130 терминов `article_slug`
пуст, статью нельзя завести без релиза приложения.

Это блокирует три разных направления сразу:

| Направление | Что упирается |
|---|---|
| Atlas | 130 терминов ведут в никуда; SEO-запросы вида «что такое кизил в вине» некуда посадить |
| Витрины | страница конкурса и винодельни, ссылка партнёру без «установите приложение» |
| Туризм | QR на офлайн-точке ведёт человека **без приложения** — публичная страница обязательна |

Перенос статей в БД планировался дважды — в архитектуре локализации 21.06
(таблица `wine_atlas_entries`) и в видении карточки 29.07 («сегодня статей 6 и
они в seed; завтра они в БД») — и оба раза откладывался.

## 2. Главное архитектурное решение

**Строим не «статьи Atlas в базе», а общий публикационный контур.**

ТЗ туризма от 01.06 прямо предостерегает: публичные страницы «не должны
становиться отдельными вручную поддерживаемыми лендингами». Если сделать
издательский слой под статьи Atlas, через полгода туризм придёт со своими
страницами и появится второй такой же движок.

Общее у всех потребителей одно и то же:

```
сущность с секциями → медиа → статус публикации → снимок → публичный маршрут
```

Разный только субъект: **термин Atlas, конкурс, винодельня, тур**.

Статьи Atlas — первый потребитель контура, а не его смысл.

## 3. Цели и не-цели

### 3.1. Цели

1. Статьи живут в БД и редактируются в админке без релиза приложения.
2. Шесть существующих статей перенесены из кода без потери содержания.
3. Термин Atlas может иметь статью; карточка вина ведёт в неё.
4. Структура страницы — секции, а не одно текстовое поле.
5. Конкурсы заведены как сущность; награда ссылается на конкурс, а не на строку.
6. Публичные маршруты спроектированы, даже если веб-версия ещё не собирается.
7. Справочник географии принимает апелласьон, и накопленная очередь
   разбирается (добавлено 08.08.2026, см. §8).
8. Предложение, пришедшее раньше своего термина, встаёт на место само
   (добавлено 08.08.2026, см. §9).

### 3.2. Не-цели этой сессии

- Наполнение контентом. Пишем только перенос шести статей; обязательств по
  объёму нет. ИИ-черновики показали слабое качество (повторы, статьи близкие по
  смыслу) — отдельная работа.
- Веб-сборка Flutter web как продукт. Проектируем маршруты и снимок, собираем
  позже.
- Платное размещение, владение страницей партнёром, биллинг.
- Туризм. Контур обязан его выдержать, но реализуется он своей сессией.

## 4. Модель данных

### 4.1. Страница

```sql
create table public.content_pages (
  id            uuid primary key default gen_random_uuid(),
  subject_type  text not null,     -- atlas_term | competition | winery | article | tourism
  subject_id    uuid,              -- ссылка на atlas_terms/wineries/…, null для свободной статьи
  slug          text not null unique,
  locale_base   text not null default 'ru',
  title         text not null,
  subtitle      text,
  summary       text,              -- 1–2 строки, показывается там, где нет места статье
  category      text,              -- «Регион», «Сорт», «Аромат», «Конкурс»
  read_time_min integer,
  hero_image_url    text,
  hero_image_path   text,
  accent_color      text,
  hero_tags         text[] not null default '{}',
  status        text not null default 'draft',   -- draft | review | published | archived
  published_at  timestamptz,
  published_snapshot jsonb,        -- то, что отдаётся публично, см. §4.4
  created_by uuid, updated_by uuid,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
```

`subject_type` — то, ради чего контур общий. Первый релиз использует
`atlas_term` и `article`; `competition` появляется в §7, `winery` и `tourism`
позже без изменения схемы.

### 4.2. Секции

Состав `section_type` берётся из ТЗ туризма §17, чтобы не проектировать заново:

```sql
create table public.content_page_sections (
  id           uuid primary key default gen_random_uuid(),
  page_id      uuid not null references public.content_pages(id) on delete cascade,
  section_type text not null,   -- hero | story | terroir | winemaker | vineyards
                                -- | wines | gallery | facts | faq | atlas_links | custom
  title        text,
  subtitle     text,
  body_markdown text,
  media        jsonb not null default '[]',      -- [{url, path, caption, alt}]
  linked_wine_ids uuid[] not null default '{}',
  linked_page_ids uuid[] not null default '{}',
  linked_term_ids uuid[] not null default '{}',
  wine_query   jsonb,           -- поисковый запрос и фильтры каталога, см. §4.3
  display_style text not null default 'standard',
  sort_order   integer not null default 0,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
```

**Скелет, а не полная реализация.** В первом срезе редактор поддерживает три
типа: `story` (заголовок + markdown), `gallery` (медиа) и `wines` (подборка).
Остальные типы существуют в enum и валидируются, но UI под них появится позже.
Так структура заложена, а объём работ ограничен.

### 4.3. Подборка вин

Переносим механику `AtlasWineLink` как есть: поисковый запрос, запасные
запросы и фильтры каталога.

```json
{
  "title": "Попробовать рислинг",
  "query": "рислинг",
  "fallback_queries": ["riesling"],
  "note": "Сухие образцы Мозеля",
  "filters": { "colors": ["white"], "types": ["still"], "sugars": ["dry"] }
}
```

Прямые `linked_wine_ids` — для случаев, когда подборка фиксированная
(вина-победители конкурса).

### 4.4. Опубликованный снимок

`published_snapshot` — собранная страница со всеми секциями и разрешёнными
ссылками в одном JSON. Причина: публичный маршрут и SEO-страница не должны
собирать страницу шестью запросами и не должны видеть черновики.

Снимок пересобирается при публикации. Черновик читается только админом и
только из живых таблиц.

### 4.5. Связь с термином

Существующее поле `atlas_terms.article_slug` остаётся контрактом карточки —
менять её не нужно. При публикации страницы с `subject_type='atlas_term'`
триггер проставляет `article_slug` соответствующему термину, при снятии с
публикации — очищает.

### 4.6. RLS

- `content_pages`, `content_page_sections`: публичное чтение **только**
  `status='published'`; полный доступ — `is_catalog_admin`.
- Публичный клиент читает снимок, а не секции. Секции открыты админу.

Это прямой урок из истории `wine_terms`: тогда RLS отдавала архивные строки
администратору, и модератор видел в карточке то, что уже убрал. Здесь фильтр
статуса ставится и в политике, и в запросе.

## 5. Перенос шести статей

Источник: `lib/features/atlas/data/atlas_articles_seed.dart` — `bordeaux-without-stress`,
`krasnodar-krai`, `cabernet-sauvignon`, `crimea-wines`, `tuscany-without-pomp`,
`riesling-first-glass`.

Требования:

1. Перенос **скриптом**, а не руками: seed → SQL, чтобы результат
   воспроизводился и проверялся.
2. Тело markdown разбивается на секции `story` по заголовкам второго уровня.
   Если разбиение не однозначно — вся статья одной секцией; это допустимо.
3. `wineLinks` → секция `wines` с сохранением запросов и фильтров.
4. Английские версии полей сохраняются, см. §11.
5. После переноса файл seed **удаляется**, провайдер читает БД. Промежуточного
   состояния «часть в коде, часть в базе» быть не должно.
6. Громкая проверка: если перенеслось не шесть статей — миграция падает.

## 6. Редактор в админке

Экран «Atlas → Страницы». Требования:

- список с фильтром по статусу и типу субъекта, поиск по заголовку;
- создание страницы: тип субъекта, привязка к термину через существующий
  подбор терминов, slug с автогенерацией и проверкой уникальности;
- редактор секций: добавить, удалить, переупорядочить, три рабочих типа;
- markdown с предпросмотром;
- загрузка медиа в бакет **`content_pages`** через существующий
  `StorageService.uploadPublicFile` — тот же путь, что у `wine_images` и
  `winery_banners`, ничего нового не заводим;
- предпросмотр страницы целиком до публикации;
- публикация и снятие с публикации с пересборкой снимка;
- аудит: кто и когда опубликовал.

**Подача редактора** — через `showAdminEditorSurface`, добавленный 06.08.2026:
панель снизу на телефоне, окно на вебе. Отдельных решений не принимать.

## 7. Справочник конкурсов

### 7.1. Проблема, подтверждённая данными

В очереди 15 предложений наград на 8–9 реальных сущностей:

- **Decanter** (×2) и **Decanter World Wine Awards** (×2) — один конкурс;
- **Simple Wine News**, **Simple Wine News, рейтинг лучших российских игристых
  вин**, **Лучшие российские вина 2025/2026 по версии SWN** — одно издание;
- **James Suckling · 90 points** — **не конкурс, а критик**.

### 7.2. Два класса сущностей

Модель обязана их различать, иначе «золото» и «90 баллов» встанут в один ряд:

| Класс | `kind` | Пример | Что показывает награда |
|---|---|---|---|
| Конкурс | `award_program` | Decanter World Wine Awards | уровень медали |
| Рейтинг критика | `rating_source` | James Suckling, Decanter | баллы по шкале |

У `rating_source` добавляется шкала (`score_scale`: 100, 20, звёзды), чтобы
«три звезды» и «91 балл» не сравнивались напрямую.

### 7.3. Заведение

- термины `award_program` и `rating_source` заводятся как обычные термины
  Atlas — со статьёй через тот же контур;
- у награды `program_term_id` становится **основным** путём, свободный
  `program_name` остаётся только запасным для импорта;
- форма награды: выбор программы обязателен либо явное «нет в справочнике →
  создать»;
- выбор программы **подтягивает** логотип, лицензию и источник изображения из
  термина — три правовых поля исчезают из формы награды.

### 7.4. Что делать с очередью прямо сейчас

**Не применять 15 предложений наград до появления справочника.** Пока они
лежат в очереди, долга нет: это ещё предложения, а не факты. Гайд по очереди
правится соответственно.

### 7.5. Дефект, который чинится этой же сессией

Награды читаются публично **без фильтра по статусу**: политика открыта всем
(`using (true)`), запрос статус не проверяет. Неподтверждённая награда видна в
карточке наравне с подтверждённой. Это прямой пункт §22 Session 2.5
«draft/unverified не видны публично».

### 7.6. Поле `confidence` у награды

Сегодня не влияет ни на что: ни на показ, ни на автоматику, ни на порядок.
Решение: **убрать из формы**, оставив колонку для данных исследования. Держать
непонятный параметр без пояснения хуже, чем не иметь его.

## 8. География: апелласьону нужна не таксономия, а справочник мест

Добавлено 08.08.2026 по итогам разбора очереди.

### 8.1. Что уже решено и не пересматривается

Апелласьон **обязан лечь на существующий справочник географии WinePool**, а не
породить вторую географию внутри `atlas_terms`. Решение записано в итогах
Session 2.5 и подтверждено 08.08.2026. Именно из-за него 93 предложения
регионов и апелласьонов лежат в очереди неприменёнными — это пауза с
обоснованием, а не забытый хвост.

Возврат к варианту «завести апелласьоны терминами Atlas» закрыт: он даёт две
записи на одно место, и они неизбежно разъедутся.

### 8.2. Почему справочник сегодня их не принимает

```
regions: id, name, country_code, is_popular
```

Плоский список без уровня и без родителя. Ни «Шампань AOC», ни «Кубань.
Таманский полуостров» положить в него так, чтобы они отличались от области,
нельзя. Это и есть настоящая причина паузы — не качество данных, а форма
таблицы.

Что видно в 39 накопленных предложениях:

| Наблюдение | Пример из очереди | Что требуется от схемы |
|---|---|---|
| Вложенность | «Кубань» и «Кубань. Таманский полуостров» | родитель |
| Разные уровни | область, субрегион, апелласьон | уровень |
| Класс качества вместо места | `AOC`, `DOC`, `IGT`, `ЗГУ`, `VSQ`, `Vin de France` | отдельное поле, а не часть имени |
| Разнобой написаний | «ЗГУ «Кубань»» и «ЗГУ Кубань» | покрыт существующим `region_aliases` |

Строка «класс качества» — главное. `DOC` и `ЗГУ` приходят как самостоятельные
значения, хотя это не места. А если хранить класс внутри имени, «Шампань» и
«Шампань AOC» навсегда останутся разными объектами.

### 8.3. Расширение справочника

```sql
alter table public.regions
  add column parent_region_id uuid references public.regions(id),
  add column level text not null default 'region'
    check (level in ('region', 'subregion', 'appellation')),
  add column quality_class text,   -- AOC | DOC | DOCG | IGT | IGP | AVA | ЗГУ | ЗНМП
  add column slug text unique;
```

Апелласьон — строка `regions` с `level = 'appellation'`, родителем-регионом и
классом качества. Синонимы уже есть в `region_aliases` и переиспользуются без
изменений.

### 8.4. Открытый вопрос, решаемый первым делом среза

Карточка вина сегодня ждёт апелласьон как **термин Atlas**:
`wineProductionTermKinds` замыкается видом `appellation`, а
`wineSingletonTermKinds` держит правило «один на вино». Если место живёт в
`regions`, у карточки два пути:

| Путь | Цена | Риск |
|---|---|---|
| Зеркалить место термином Atlas | правка только на стороне данных | две записи на одно место — то, от чего защищает §8.1 |
| Брать апелласьон из географии вина | правка блока признаков карточки | разовая, дальше источник один |

**Рекомендация — второй.** Первый воспроизводит ровно ту ошибку, ради
исключения которой география и отложена.

При этом вид `appellation` в `atlas_terms` **остаётся**, но меняет смысл: это
не запись места, а предмет статьи — «что такое ЗГУ», «чем DOCG отличается от
DOC». Такой термин получает страницу через контур §4 и не дублирует `regions`.

### 8.5. Отсев

Значения `AOC`, `DOC`, `DOCG`, `IGT`, `IGP`, `ЗГУ`, `VSQ`, `Vin de France`
апелласьонами не становятся: это класс качества. Предложение с таким
значением отклоняется с причиной «класс качества, не место», а сам класс
проставляется полем `quality_class` у настоящего апелласьона.

## 9. Пересопоставление предложений с терминами

Добавлено 08.08.2026.

### 9.1. Чего не хватает

`matched_term_id` у предложения заполняется **только экстрактором**, в момент
загрузки. Постановка ссылки задним числом делалась вручную отдельным SQL —
так в волне 4 очередь уменьшили с 331 до 302.

Следствие: предложение, пришедшее раньше своего термина, само на место не
встаёт. Любое пополнение справочника требует ручного прогона, а правило
безопасного применения (§ `catalog_knowledge_proposal_is_safe`) требует
непустого `matched_term_id` — значит такие предложения не применятся никогда,
пока кто-то не вспомнит.

Сегодня в этом состоянии: 39 апелласьонов, 54 региона, 13 подходов, 6 методов,
15 без вида.

### 9.2. Что нужно

```sql
create function public.admin_rematch_catalog_knowledge_proposals(
  p_term_kind text default null
) returns jsonb
```

Границы намеренно узкие:

- трогает только `moderation_status = 'pending'` **и** `matched_term_id is null`;
- сопоставляет по `suggested_term_slug` и по `atlas_term_aliases`;
- ставит ссылку на **опубликованный** термин, черновой не годится;
- ничего не создаёт и ничего не применяет — только связывает;
- решённые предложения не переписывает, как и §7.2 ingest'а.

Вызывается двумя способами: автоматически после публикации термина и кнопкой
«Пересопоставить» в очереди модерации.

### 9.3. Почему это важнее, чем выглядит

Без этой функции автоматизация упирается не в модель и не в деньги, а в
человека, который должен вспомнить про ручной прогон. Каждая новая волна
терминов оставляет за собой хвост предложений, ждущих вечно.

## 10. Публичные маршруты и веб

Проектируются сейчас, собираются позже.

```
/atlas                     — список страниц
/atlas/:slug               — страница
/competition/:slug         — конкурс (тот же контур, subject_type=competition)
/winery/:slug              — витрина винодельни (позже)
/tourism/:experienceId     — тур (позже, по своему ТЗ)
```

Требования:

- маршрут отдаёт `published_snapshot`, один запрос;
- страница читается **без авторизации** и без установленного приложения — это
  условие работы QR на офлайн-точке туризма;
- на странице есть переход в приложение, но контент доступен и без него;
- лендинг `winepool.ru` может ссылаться на эти страницы, но **не хранит копию**
  контента (правило из ТЗ туризма).

## 11. Локализация

По `l10n_localization_architecture_2026_06_21.md` контент в БД локализуется
своими полями, а не ARB.

Первый срез: русский обязателен, английский опционален — поля `title_en`,
`subtitle_en`, `summary_en`, `body_markdown_en`, `hero_tags_en`, как в текущей
модели статьи. Для CIS-языков русский остаётся допустимым запасным вариантом.

## 12. Коммерческая граница

Фиксируется в архитектуре, а не в договорённостях:

- **Факт** — вино, конкурс, год, уровень, баллы, источник. Живёт в
  `wine_awards` и `wine_terms`. Редакционный, нейтральный.
- **Витрина** — описание, фотографии, логотип, промо. Живёт в
  `content_pages`. Может быть платной и может вестись партнёром.

Поиск, выдача каталога, сортировка и вес медали читают **только факты** и
никогда не читают `content_pages`. Тест на это входит в приёмку.

## 13. Критерии приёмки

1. Статья создаётся, редактируется и публикуется через админку без сборки.
2. Шесть перенесённых статей открываются с тем же содержанием, что и раньше.
3. Файл `atlas_articles_seed.dart` удалён; приложение читает БД.
4. Термин с опубликованной страницей ведёт из карточки вина в статью;
   `article_slug` проставляется и очищается автоматически.
5. Черновая страница недоступна публичному клиенту — проверено запросом от
   анонимной роли.
6. Секции добавляются, переупорядочиваются и удаляются; порядок сохраняется.
7. Медиа загружается в `content_pages` и отображается в галерее.
8. Конкурс и рейтинг критика — разные виды термина; награда ссылается на
   термин; свободный текст остаётся только запасным.
9. Награда со статусом `source_claimed` не видна в публичной карточке.
10. Публичный маршрут отдаёт снимок без авторизации.
11. Каталог и поиск не обращаются к `content_pages` — проверено тестом.
12. Миграция документирована, бэкап и контрольные суммы записаны.
13. Апелласьон заведён строкой `regions` с уровнем, родителем и классом
    качества; второй записи того же места в `atlas_terms` не появилось.
14. Карточка вина показывает апелласьон, взятый из географии вина (§8.4).
15. Значение вида `DOC` или `ЗГУ` апелласьоном не становится: предложение
    отклонено с причиной «класс качества, не место».
16. Новый термин с синонимом подхватывает лежавшие без термина предложения
    **без ручного SQL** — проверено на очереди апелласьонов.
17. Пересопоставление не трогает решённые предложения и ничего не применяет
    само — проверено запросом до и после.

## 14. Порядок работ

| Срез | Содержание | Зависит от |
|---|---|---|
| A | Схема: `content_pages`, `content_page_sections`, RLS, снимок | — |
| B | Перенос шести статей скриптом, удаление seed, чтение из БД | A |
| C | Редактор в админке: список, секции, медиа, публикация | A |
| D | Связь термин ↔ страница, `article_slug`, вход из карточки | A, C |
| E | Справочник конкурсов, правка модели наград, фильтр статуса | A, C |
| F | Публичные маршруты и снимок для веба | A, B |
| **G** | **Пересопоставление предложений (§9)** | — |
| **H** | **Расширение `regions`, разбор очереди географии (§8)** | G |

Срезы E и G не зависят от редактора и идут параллельно с C. **G ставится
раньше H намеренно**: без пересопоставления расширенный справочник придётся
сшивать с очередью руками, то есть повторить работу волны 4.

## 15. Риски

1. **Разбиение markdown на секции** при переносе может оказаться неоднозначным.
   Смягчение: разрешено переносить статью одной секцией.
2. **Снимок и живые данные разъезжаются**, если забыть пересборку. Смягчение:
   пересборка триггером при изменении секций опубликованной страницы.
3. **Контур перегружается** попыткой сразу закрыть туризм. Смягчение: типы
   секций объявлены, UI делается для трёх.
4. **Пустой Atlas.** Шесть статей на 130 терминов — это по-прежнему почти
   пусто. Смягчение: контент-план из самих терминов, по одной статье, без
   обязательств по срокам в этой сессии.
5. **Апелласьон утянет за собой всю географию.** Регионов в очереди больше,
   чем апелласьонов (54 против 39), и соблазн «раз уж полезли» велик.
   Смягчение: срез H закрывает только апелласьоны; регионы — своей работой.
