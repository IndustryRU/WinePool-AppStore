# Push-уведомления: как устроены и как добавить новое

Обновлено: 22.09.2026. Состояние и история решений —
`docs/handoffs/push_notifications_handoff_2026_09_21.md`, тестовая
отправка — `docs/rustore_push_test_send.md`.

## 1. Цепочка целиком

```
событие в базе ──► строка в очереди ──► отправщик на VPS ──► универсальный API RuStore ──► телефон
(триггер/RPC)      app_notifications     (этап 1, таймер)     RuStore + FCM одним запросом   WinePoolNotificationPresenter
```

- **Очередь.** Личные уведомления — строки `public.app_notifications`
  (`user_id`, `type`, `title`, `body`, `entity_type`, `entity_id`,
  `metadata`, `dedupe_key`). Из неё уже работают колокольчик в приложении и
  письма (`send_notification_emails.py`, таймер раз в 5 минут). Push — третий
  канал той же строки, отдельной системы уведомлений нет.
- **Какие строки пушатся** — решает триггер `app_notifications_mark_push`
  (миграция `202609221000`): новой строке служебного типа ставит
  `push_status = 'pending'`. Прежняя история и остальные типы — `null`.
- **Отправщик** — `supabase/functions/send-notification-emails/winepool_push.py`,
  зовётся из `send_notification_emails.py` тем же таймером раз в 5 минут
  (на VPS — `/opt/winepool-notifs/`). Берёт `pending`/`failed` строки,
  собирает `data` (`build_push_data`), шлёт на активные токены пользователя
  (`user_push_tokens`, `rustore` + `fcm`) одним запросом универсального API.
  Статусы: `sent`, `skipped` (нет токенов; все токены отвергнуты; строка
  старше суток), `failed` (повтор, до 5 попыток). Отвергнутый токен
  («invalid tokens») получает `is_active = false`.
- **Ключи** — `/opt/winepool-notifs/.env`: `RUSTORE_PROJECT_ID`,
  `RUSTORE_SERVICE_TOKEN`, `FCM_SERVICE_ACCOUNT_JSON` (путь к ключу Firebase
  там же, права 600). Без них push выключен, письма идут как раньше.
- Задержка — до 5 минут (период таймера).
- **Телефон.** Сообщение приходит по обоим каналам; универсальная библиотека
  показывает его один раз. Рисует и ведёт по нажатию только
  `WinePoolNotificationPresenter.kt`.

## 2. Контракт полей `data`

Сообщения только data-only: блок `notification` не слать — SDK нарисует
второе уведомление на своём канале.

| Поле | Обязательно | Что значит |
|---|---|---|
| `type` | да | тип из `app_notifications.type` — для аналитики и частных случаев |
| `label` | нет | что это за сообщение — мелко в шапке после «WinePool»: «Новый отзыв о вине», «Статус заявки» … |
| `title` | да | первая крупная строка (жирная) — главное: название вина, винодельни, тура |
| `body` | да | вторая строка — подробности; длинный текст разворачивается целиком |
| `link` | нет | путь экрана приложения, куда вести по нажатию: `/wine/<id>`, `/review/<токен>`, `/tourism/trip/<leadId>`, `/notifications` … Без `link` — просто открыть приложение |
| `channel` | нет | `service` (по умолчанию) — «Служебные», `news` — «Новинки и отзывы» |
| `image_url` | нет | картинка: крупно в развёрнутом виде, миниатюрой в свёрнутом. Не загрузилась за 5 с — уведомление показывается без неё |

Правило раскладки: тип сообщения — в `label`, а `title` и `body` целиком под
полезное. Не «Новинка в каталоге / Q Бордо-бленд», а `label` «Новинка в
каталоге», `title` «Q Бордо-бленд», `body` «Fanagoria · Краснодарский край ·
от 890 ₽».

Размер сообщения — до 4096 байт. Частный случай с собственным видом один:
`catalog_wine_new` (поля `wine_id`, `wine_name`, `winery`, `region`,
`price_label`): приложение само раскладывает их по правилу выше.

## 3. Нужна ли новая версия приложения

**Не нужна**, если новое уведомление укладывается в контракт: свои
заголовок, текст, картинка, один из двух каналов и переход на экран, который
в приложении уже есть. Это делается целиком на сервере: триггер или функция
кладёт строку в очередь, отправщик знает, какой `link` поставить.

**Нужна**, если требуется:
- экран, которого в приложении ещё нет (адрес для `link` появляется только с
  версией, где он добавлен);
- особый вид (кнопки прямо в уведомлении, свой макет, как у «Новинки в
  каталоге»);
- третий канал в настройках Android;
- подписка на темы RuStore/FCM (делается в коде приложения).

Всё это уже заложено в версию, которая выйдет после 1.1.0: адреса
`/review/<токен>` (оценка поездки) и универсальный `link`, два канала. В
1.1.0 из магазина push нет вообще — первая версия с push обязательна.

## 4. Как добавить новый тип — по шагам

1. **Решить, служебное это или рассылка.** Служебное — ответ на действие
   человека (его заявка, его отзыв, его поездка): канал `service`.
   Рассылка многим о винах — канал `news`, и **до запуска — вопрос юристу**
   (реклама алкоголя, ст. 21 и 18 38-ФЗ; п. 6 handoff). Рассылки — только тем,
   кто не выключил их в настройках (этап 1, п. 5 плана). **Все настройки
   включены по умолчанию** (решение владельца 22.09.2026): и каналы Android,
   и серверные переключатели типов; человек выключает сам.
2. **Выбрать экран для `link`.** Если его нет в `lib/core/router.dart` —
   это работа для версии приложения (п. 3). Экран, требующий входа, сам
   отправит на вход и вернёт обратно.
3. **Источник строки.** Для личного уведомления — там, где событие уже
   рождается: триггер или RPC добавляет строку в `app_notifications`
   (образец — `tourism_queue_notification(...)`, карта переиспользования).
   Отдельный источник push не заводить.
4. **Сервер — три места:**
   - тип в список триггера `app_notifications_mark_push_v1` (новая миграция,
     применять под `-U supabase_admin`);
   - подпись шапки в `LABELS` и, если нужно, правило `title` / `body` /
     `link` в `build_push_data` (`winepool_push.py`); без правила уйдут
     `title` и `body` строки очереди, а нажатие просто откроет приложение;
   - выложить оба файла в `/opt/winepool-notifs/` (резервная копия — рядом).
   Остальные типы продолжают идти только письмом и в колокольчик.
5. **Проверить на телефоне** до серверной части — тестовым скриптом, без
   правки кода:
   ```powershell
   python scripts/send_universal_push.py --type <тип> --label "…" --title "…" --body "…" --link /… [--channel news] [--image https://…]
   ```
   Проверить: пришло одно уведомление; нажатие ведёт на нужный экран — при
   открытом приложении и при смахнутом из недавних.
6. Отметить тип в таблице п. 5 этой инструкции.

## 5. Типы: что есть и что планируется

| Тип | Кому | Канал | `link` | Состояние |
|---|---|---|---|---|
| `catalog_wine_new` | многим | news | `/wine/<wine_id>` | только ручная отправка; **ждёт юриста** |
| `tourism_lead_status_changed` | автору заявки | service | `/tourism/trip/<lead_id>` | **работает** с 22.09.2026 |
| `tourism_lead_operator_message` | автору заявки | service | `/tourism/trip/<lead_id>` | **работает** |
| `tourism_ticket_delivery_updated` | автору заявки | service | `/tourism/trip/<lead_id>` | **работает** |
| `review_approved` / `review_rejected` | автору отзыва | service | `/wine/<wine_id>` | **работает**; `title` — «★★★★☆ <вино>» |
| `draft_submission_approved` / `_changes_requested` / `_rejected` | автору | service | одобрено — `/wine/<id>`, иначе `/draft-wines/<id>` | **работает** |
| `visit_review_request` | гостю после «Состоялась» | service | `/review/<токен>` | этап 2, ТЗ H1-02E §4.13 |
| `wine_review_published` | всем | news | `/wine/<wine_id>` | идея; **ждёт юриста** |

### Пример: «Как прошёл вечер?» (ТЗ H1-02E §4.13)

- Когда: на следующий день после статуса «Состоялась», не раньше 11:00.
- Строка очереди: `type = visit_review_request`, `user_id` — автор заявки,
  `entity_type = tourism_lead`, `entity_id` — заявка.
- Токен оценки выдаёт функция по своей заявке (`created_by = auth.uid()`,
  п. «Этап 2» handoff); отправщик кладёт `link = /review/<токен>`.
- Текст: «Как прошёл вечер в <винодельня>? ★★★★★», канал `service`.
- Нажатие открывает оценку в одно касание — экран тот же, что на сайте.

### Пример: новый отзыв о вине — всем

Это рассылка, а не личное уведомление, поэтому в `app_notifications` (по
строке на человека) она не ложится: колокольчик у каждого заполнился бы
чужими отзывами. План:
- отдельная очередь рассылок (одна строка на событие: тип, заголовок,
  текст, `link`, картинка);
- отправщик раздаёт её пачками по всем активным токенам тех, кто не
  выключил «Новинки и отзывы»; темы RuStore/FCM не нужны — список токенов у
  нас есть, и так проще учитывать настройки;
- `type = wine_review_published`, `channel = news`, `link = /wine/<wine_id>`,
  `image_url` — фото бутылки;
- раскладка: `label` «Новый отзыв о вине», `title` — **сначала оценка, потом
  название**: «★★★★★ Q Бордо-бленд» (длинное название обрежется, звёзды
  останутся видны), `body` — начало текста отзыва в кавычках;
- частота (решение владельца 22.09.2026): **уведомление на каждое новое
  событие**, без сводок — пользователей пока немного. Сводку раз в день
  вернуть к обсуждению, если рассылку начнут выключать.

**Запуск — только после ответа юриста.** Уведомление неопределённому кругу
лиц о конкретном вине может быть признано рекламой алкоголя.

## 6. Проверка на телефоне

Push проверяется только на реальном устройстве и только в релизной сборке
(подпись должна совпадать с проектом RuStore). Сборку ставит сессия по USB
(`CLAUDE.md` §7). Минимальный набор: открыто / свёрнуто / смахнуто из
недавних / «Очистить» в недавних / экран выключен. Force-stop не
использовать: после него Android не доставляет push, пока приложение не
откроют вручную.
