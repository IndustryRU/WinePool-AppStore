3. **Admin доступ только через роль:** `/admin/*` сохраняется, но показывается только пользователям с `role = admin` в Supabase. Обычный пользователь не видит ни одной entry-point в навигации.
4. **Убрать "купить" CTA с карточки вина** ([wine_details_screen.dart](../lib/features/wines/presentation/wine_details_screen.dart)). Заменить на `Добавить в погребок` (если есть) / `Добавить в список желаний` (простой bookmark, новый тонкий слой).

6. **Локализация pass:** все strings через ARB, заглушки на EN убраны или минимизированы.
7. **Аудит crash-surface:** прогнать главные флоу, зафиксировать известные крэши, починить критичные. Включить Sentry (или аналог — Firebase Crashlytics).

10. **Receipt geolocation:** `shop_address/shop_name` из чека → Supabase Edge Function `geocode-receipt` → Yandex Geocoder REST → `user_receipts.lat/lng/geocoded_at`. В review показывать карту до сохранения, при сохранении переиспользовать найденные координаты.
11. **Draft/admin map provenance:** в черновике и модерации показывать место покупки из чека, цену, адрес, координаты и карту. Если адрес есть, но координат нет, дать кнопку `Определить` для ручного дорасчёта.

    - `В каталоге` → карточка вина, `Черновик` → разбор черновика, `Из чека` → информационная карточка;
    - фото из `wines.image_url` или `draft_wines.photo_url`, fullscreen preview по тапу.

### Критерии готовности

- Свежий билд, установленный с нуля, не содержит ни одной видимой ссылки на commerce/seller/admin для обычного пользователя.
- Age gate отрабатывает на первом запуске.
- Sentry получает события из debug-билда.
- Crash-free sessions на внутреннем тестировании ≥99%.
- В receipt review после разбора чека появляется блок `Место покупки` с async-геокодингом, который не блокирует сохранение.
- Старый черновик с адресом и без координат можно вручную догеокодировать кнопкой `Определить`.
- Карточка вина не использует seller offers для MVP-цены; цена строится по реальным чекам или честно показывает отсутствие данных.
- `Моя винная карта` показывает реальные точки покупок текущего пользователя.
- Из точки магазина можно открыть список вин и перейти в карточку каталога или черновик.
- Черновики с фото показывают пользовательское фото; каталожные вина показывают бутылку из каталога.
- На этом этапе карта считается feature-complete для MVP; новые map-фичи не добавлять до релизной стабилизации.

## Неделя 2: онбординг + активационная петля

Цель: довести путь "установил → добавил первое вино" до 60+ секунд времени и ≥50% conversion на внутреннем тестировании.

### Задачи

1. **Onboarding 3 экрана:**
   - Экран 1: "Добро пожаловать в WinePool" + value prop одной строкой
   - Экран 2: "Сканируй чек из винотеки — бутылка сама окажется в твоём погребке" (анимация или скриншот-демо)
   - Экран 3: "Твой винный дневник, который всегда с тобой" + CTA `Начать`
2. **Empty-state погребка:** ([my_cellar_screen.dart](../lib/features/cellar/presentation/my_cellar_screen.dart)) — большая кнопка `Отсканировать чек` + alt-кнопка `Добавить вручную`.
3. **Быстрый flow "добавить вручную":** search → tap → "Добавить в погребок" за 3 тапа. Без обязательных полей дегустации/даты на входе.
4. **Receipt scan polish:** входной экран `/receipt-qr-scanner` с пояснением "какие чеки работают" (список поддерживаемых ритейлеров) и понятной ошибкой при неудачном сканировании.
5. **Первое событие в analytics:** `onboarding_completed`, `first_wine_added`, `first_receipt_scanned`, `first_tasting_logged`. Без этих событий нельзя измерить activation.

7. **Map loop QA:** `Моя винная карта` → точка магазина → `Вина из магазина` → карточка вина / черновик → fullscreen фото → back-навигация без потери состояния.

### Критерии готовности

## Что делать на неделе 7+ (post-MVP)

Документ не покрывает то, что идёт после релиза — но важно обозначить принципы:

1. **Первые 2 недели post-release:** никакого нового скоупа. Только bug-fix, UX-polish на основе feedback, catalog coverage (докидываем недостающие позиции, которые появились в чеках пользователей).
2. **Первый большой пост-MVP slice:** геймификация (бейджи) ИЛИ расширение редакции (больше материалов + "Вино дня") — зависит от того, какая метрика отстаёт (activation или retention).
3. **Winery layer:** после MVP отдельно проработать публичный слой виноделен. Цель — не просто справочник, а связка `винодельня -> её вина -> материалы атласа -> пользовательские покупки/дегустации -> партнёрский статус`, с аккуратной редактурой, правами на фото и флагом публикации. Текущий блок в карточке вина считать seed-версией этого направления.
4. **Curated wine links для атласа:** после Week 4.5 оценить качество связки `article -> catalog filters`. Если фильтров каталога недостаточно, заменить MVP-поиск/fallback на редакционные подборки конкретных вин: `article -> recommended_wines -> wine_details`, с порядком, подписью редактора, fallback на похожие вина и мониторингом битых ссылок.
5. **Горизонтальное меню buyer-home:** вернуть после MVP не как витрину будущих разделов, а как короткую строку живых быстрых действий (`Сканировать`, `Погребок`, `Карта`, `Атлас`, `Избранное`) после проверки первых пользовательских сценариев.
6. **Личные магазины и ручная привязка покупки:** чековый слой уже собирает магазины через `shop_geo_key`, координаты и карту. Post-MVP нужно превратить это в личный справочник мест:
   - пользователь может дать магазину короткое имя (`Пятёрочка у дома`) поверх длинного юридического названия из чека;
   - пользователь может пометить магазин как избранный/частый;
   - карта показывает пользовательское имя, но сохраняет исходное имя/адрес/координаты для гео-логики;
   - ручное добавление вина в погребок может выбрать магазин: сначала избранные, затем весь список посещённых;
   - выбранный магазин привязывает ручную покупку к той же точке карты, что и покупки из чеков;
   - в профиле или карте нужен вход в управление личными магазинами: переименовать, снять избранное, объединить очевидные дубли точек.
7. **Абузконтроли Phase 1/2:** когда появится реальный трафик и первые попытки спамить drafts — тогда и не раньше.
8. **Коммерческая механика:** только после того, как есть ≥1000 активных пользователей и хотя бы 1 реальный B2B-разговор с винотекой.

## Риск-списки для каждой недели (коротко)

## Короткий итог

6 недель разработки + 1 неделя подготовки. Скоуп жёсткий: онбординг, погребок, сканирование чеков, карточка вина, редакционный буклет, мини-друзья, ничего сверх. Cut: commerce, seller, admin, social feed, gamification. Цель — не "миллионы пользователей", а **500–3000 установок и 100–400 активных с погребком, доказанная activation × retention гипотеза, основа для роста и commercial conversations.**

Все последующие слои (геймификация, редакционный Daily Wine Index, расширенный атлас, B2B API, партнёрская commerce-модель) делаются после, когда есть данные, а не до, когда есть только гипотезы.
