# Как продавец попадает в WinePool

Дата: 07.08.2026
Статус: решение на 1.1.0 — оставляем самый простой канал; приглашение по почте
проектируется здесь и строится вместе с кабинетом продавца

---

## 1. Три возможных канала

| Канал | Кто заводит аккаунт | Состояние |
|---|---|---|
| **A. Самозапись через регистрацию** | Продавец сам, режим «бизнес» | Код есть, выключен вместе с `commerceEnabled`. Решением владельца 07.08.2026 на экран регистрации **не возвращается** |
| **B. Заводим мы, аккаунт продавца уже есть** | Продавец регистрируется как обычный пользователь, мы передаём ему бизнес | **Работает сегодня** |
| **C. Приглашение по почте** | Мы создаём аккаунт по адресу продавца, он подтверждает письмом | Не построено, см. §3 |

## 2. Что делать сейчас — канал B

1. Человек из магазина регистрируется в приложении обычным пользователем.
   Подтверждение почты уже работает: `GOTRUE_MAILER_AUTOCONFIRM=false`,
   письмо уходит через Яндекс SMTP.
2. Администратор в админке: **Бизнесы → Создать продавца**, кнопка
   **«Выбрать владельца»**, поиск по почте.
3. Либо, если продавец создан раньше: карточка продавца → **«Сменить
   владельца»**.

Роль `seller` человек получает автоматически, прежний владелец остаётся в
команде менеджером.

Это ноль новой разработки и полностью рабочий сценарий. Для сети, которая
«не готова ставить приложение», подходит так же: аккаунт заводит любой её
сотрудник с рабочей почты, дальше всё делаем мы.

## 3. Приглашение по почте — проект, не реализация

Замысел: администратор вводит почту, продавцу уходит письмо «для вас
заводится магазин такой-то, подтвердите доступ», он задаёт пароль и сразу
попадает в свой бизнес.

GoTrue это умеет (`inviteUserByEmail`), и половина обвязки уже стоит. Но
проверка 07.08.2026 нашла три препятствия, каждое из которых надо снять
до, а не после запуска:

| Препятствие | Что именно |
|---|---|
| Нет русского шаблона приглашения | Заданы `SUBJECTS_CONFIRMATION` и `SUBJECTS_RECOVERY`, для invite — ничего. Письмо уйдёт стандартным английским текстом GoTrue |
| Некуда возвращать | `GOTRUE_SITE_URL = https://winepool.ru` — лендинг, где нет страницы задания пароля. `GOTRUE_URI_ALLOW_LIST` содержит только диплинк приложения для сброса пароля |
| Ключ сервисной роли | `inviteUserByEmail` требует `service_role`. В веб-админку его класть **нельзя** ни при каких условиях: он окажется в браузере. Приглашение обязано идти через edge-функцию, как `geocode-receipt` |

Побочное наблюдение: шаблоны писем подтверждения и восстановления заданы
как `http://91.227.18.214/email-confirm.html` — по IP и без TLS. GoTrue
забирает их сам, на пользователя это не влияет, но при переезде или смене
адреса письма молча станут пустыми. Отдельная мелкая работа.

## 4. Почему не сейчас

Приглашение осмысленно тогда, когда есть куда приглашать. Кабинета продавца
нет: человек получит письмо, задаст пароль, войдёт — и увидит подпись
«скоро появится». Это хуже, чем не звать вовсе.

Плюс письмо пришлось бы писать дважды: сейчас — «подтвердите аккаунт», а с
кабинетом — «вот ваш магазин, вот что с ним делать». Второе письмо
заменит первое целиком.

## 5. Что войдёт в ТЗ кабинета продавца

- edge-функция `invite-business-owner`: администратор → почта + бизнес →
  приглашение; сервисный ключ только на сервере;
- русский шаблон приглашения, называющий магазин по вывеске;
- страница задания пароля на домене, добавленном в `URI_ALLOW_LIST`;
- `business_members` уже готова — приглашать можно не только владельца, но и
  менеджера в существующий бизнес;
- первый вход ведёт сразу в кабинет своего магазина, а не на общий экран.
