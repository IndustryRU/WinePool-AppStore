# Сессия 2 · Подэтап 3b — field-level diff и разрешение полей модератором

Дата фиксации: 25.07.2026
Статус: implemented — UI-only, миграция не требуется (25.07.2026)
Родитель: `docs/catalog_fast_search_session_2_tz_2026_07_18.md`, раздел 16.3
Предшественник: подэтап 3a (`..._subetap3a_cross_user_release_dedup_tz_2026_07_25.md`)

## 1. Цель

После 3a у одной заявки может быть несколько контрибьюторов с разными значениями
полей (`snapshot_payload.contributions`). Дать модератору **field-level diff**:
по каждому полю видеть значения-кандидаты от участников и одним тапом применять
нужное в форму проверки. Затем — обычные сохранение и одобрение.

## 2. Что уже есть (аудит 25.07.2026)

- Диалог `_ReleaseProposalReviewDialog` редактирует поля релиза (год/NV, название,
  объём, алкоголь, штрихкод, отличия) и сохраняет через RPC
  `update_wine_release_proposal`.
- `update_wine_release_proposal` пишет значения в snapshot/draft и логирует событие
  `release_proposal_corrected` с выбранными значениями — то есть **резолюция полей
  уже аудируется**.
- `admin_review_wine_release_proposal` при одобрении **связывает дубль с
  существующим релизом**, если для идентичности уже есть `wine_vintage`, иначе
  материализует новый из snapshot.
- 3a: `snapshot_payload.contributions` содержит значения полей с авторством
  (admin/audit only) и `contributor_count`.

Вывод: недостающая часть 3b — только **UI field-level diff и per-field выбор**.
Backend-резолюция, аудит и линковка дубля уже покрыты. Миграция не требуется.

## 3. Реализация (UI-only)

- В `_ReleaseProposalReviewDialog` для каждого редактируемого поля собрать
  distinct значения-кандидаты из `snapshot.contributions` (год/NV, название,
  объём, алкоголь, штрихкод, отличия), с числом участников на значение.
- Под полем показывать компактные чипы-кандидаты; тап заполняет поле этим
  значением. Личности контрибьюторов не показываются — только значение и счётчик.
- Блок показывать, когда есть ≥1 кандидат от участников (наиболее полезно при
  расхождениях). При одном контрибьюторе диф не загромождает форму.
- Сохранение и одобрение — существующим путём (`updateWineReleaseProposal` →
  `reviewWineReleaseProposal`); резолюция фиксируется событием
  `release_proposal_corrected`, авторство — в `contributions`.

## 4. Не входит

- Отдельная серверная запись «поле подтверждено из кандидата K» сверх текущего
  `release_proposal_corrected` (текущего аудита достаточно).
- Приоритет очереди по истории вкладов — подэтап 3c.
- Локализация вшитых RU-строк — общий отложенный проход (см. l10n-документ).

## 5. Приёмка

- при нескольких контрибьюторах модератор видит под полями значения-кандидаты с
  числом участников и применяет их одним тапом;
- при одном контрибьюторе форма выглядит как раньше;
- сохранение пишет выбранные значения в snapshot и событие
  `release_proposal_corrected`; одобрение материализует/связывает релиз с этими
  значениями;
- static analysis чист; ни один путь не вызывает AI/внешний search.
