# Session 2.5 — аудит путей записи в погребок

Дата: 01.08.2026.

## Инварианты

- `user_storage` хранит отдельные приобретения/партии; интерфейс агрегирует их по
  смысловой идентичности `wine_id + vintage/NV` и раскрывает даты, цены и места.
- `wine_vintage_id` уточняет канонический релиз, но legacy-строка без UUID и
  каноническая строка того же года не должны образовывать две карточки.
- Повтор одного действия не должен повторно увеличивать количество: каждый
  клиентский путь передаёт стабильный `p_idempotency_key`.
- Чековая бутылка должна ссылаться и на `source_receipt_id`, и на конкретный
  `source_receipt_item_id`, иначе последующая коррекция распознавания небезопасна.

## Проверенные пути

| Путь | Статус после аудита |
|---|---|
| Карточка вина / кнопка «Добавить в погребок» | Единый confirm-sheet передаёт `wine_vintage_id` и idempotency key. |
| Ручной поиск существующего вина | Передаёт выбранный релиз, год/NV и idempotency key. |
| Предложение нового релиза | Покупка создаётся сразу; approve-trigger больше не запускает второй legacy auto-add. |
| Ручное добавление неизвестного вина | Generic approved-draft auto-add сохранён: здесь он нужен, потому что канонического вина до модерации нет. |
| Сканирование чека | Строка чека теперь создаётся до бутылки; в погреб передаются `source_receipt_item_id`, устойчивый idempotency key и release identity точного однозначного product-code match. |
| Заказ со статусом `delivered` | Передаются винтаж оффера и idempotency key `order + item`; повторная установка статуса не дублирует бутылки. |

## Production-факт и исправление

- До исправления: 120 строк `user_storage`, из них 47 чековых; 27 старых чековых
  строк не имели `source_receipt_item_id`.
- Найден ровно один доказанный фантомный дубль release-proposal: `Maré Viva
  Tinto 2025` у одного пользователя.
- Миграция `20260801_unify_cellar_release_storage_identity.sql`:
  - исключает `new_release_for_existing_wine` из generic approved-draft auto-add;
  - защищает как trigger, так и прямой вызов функции;
  - переносит provenance доказанного дубля в исходную покупку;
  - удаляет только строку с тем же пользователем, вином, годом, датой, ценой,
    количеством и общим draft-source.
- После применения: точных дублей этого типа — `0`; повторный legacy-вызов для
  release proposal возвращает `0`.

## Осознанные ограничения

- Старые 27 чековых строк без `source_receipt_item_id` не исправляются массово:
  без точного provenance автоматический backfill может связать не ту покупку.
- Текстовое совпадение строки чека определяет вино, но не всегда релиз. UUID
  релиза сохраняется только при однозначном product-code match; год нельзя
  выдумывать без подтверждения.
- Текущая модель offer до Session 2.6 хранит `vintage`, но ещё не
  `wine_vintage_id`. Заказ защищён от дублей и сохраняет год; полноценная
  release-aware связь оффера остаётся задачей архитектуры 2.6.
