## 2. Зафиксированные решения владельца

- Карточка — один длинный экран с вертикальной прокруткой, а не набор экранов.
- Бутылка остаётся визуально закреплённой в hero; раскрытие полного названия и
  описания сдвигает нижний контент, но не бутылку и не подписи winery/line.
- Рядом с названием используется компактный chevron, не кнопка
  «Показать полностью».
- `Резерв` выводится только как реальная линейка из `wine_lines`, а не как
  автоматически угаданный класс вина.
- Реальная линейка является переходом в каталог с фильтрами по винодельне и
  линейке; при отсутствии `line_id` переход не показывается.
- Выпуски строятся по `wine_vintages`; `release_name` является частью подписи
  релиза. В пользовательском интерфейсе используется единый термин «Релиз»;
  публично не показываются pending/disabled-релизы.
- Селектор выпуска остаётся однострочным; активность обозначает только близкое
  золотое подчёркивание, без второй галочки.
- Разделы называются «О вине» и «Сорта винограда».
- «О вине» — горизонтальная лента без сжатия; сорта остаются равновысокой
  двухколоночной композицией и переходят в одну колонку при крупном тексте.
- Награды имеют собственные данные и визуальные медали; при отсутствии эмблемы
  конкурса используется нейтральная премиальная заглушка.
- Экологические признаки и производственные методы не смешиваются в один
  неранжированный список: сначала признаки выбора, затем методы/происхождение.
- В карточке показываются только ароматы конкретного вина; общего списка
  «все восемь» нет. Переход ведёт в Атлас WinePool.
- Вкус использует непрерывные золотистые полосы и шкалу `0–5`; десять точек не
  используются. Строка с отсутствующим значением скрывается.
- Гастрономические сочетания используют индивидуальные иконки вместо emoji.
- Карта относится только к разделу «Где купить» и показывает магазины. Служебные
  объяснения про геолокацию и километры не выводятся.
- Карточка винодельни использует затемнённый cover, логотип, короткое описание и
  факты. Отзыв показывает цену покупки, если она известна.
- Нижнее действие «Добавить в погребок» остаётся закреплённым и не перекрывает
  последний контент.

## 4. Архитектурный подход

Это не полный rewrite. Сохраняются работающие маршруты, действия, репозитории и
публичные сценарии; экран постепенно переводится на отдельный presentation model
и небольшие секции.

Предлагаемая структура:

```text
lib/features/wines/
  application/
    wine_card_provider.dart
  domain/
    wine_card_view_data.dart
    wine_award.dart
  presentation/
    wine_details_screen.dart
    wine_details/
      wine_card_tokens.dart
      wine_card_hero.dart
      wine_release_selector.dart
      wine_facts_section.dart
      wine_grapes_section.dart
      wine_awards_section.dart
      wine_features_section.dart
      wine_aromas_section.dart
      wine_taste_section.dart
      wine_pairings_section.dart
      wine_shops_section.dart
      wine_winery_section.dart
      wine_reviews_section.dart
      wine_card_bottom_action.dart
```

`WineCardViewData` собирает стабильное базовое вино и выбранный релиз. UI не
делает SQL-предположений и не выводит release-specific данные из офферов.

Состояние выбора хранит `selectedReleaseId`, а не только `int? vintage`. Для NV и
двух релизов одного года это обязательное различие.

## 5. Границы Session 2.5 и 2.6

### Входит в Session 2.5

- read model релиза и корректный selector;
- release-aware hero, название выпуска, фото, описание, ABV, grapes и awards;
- новый визуальный порядок и все секции карточки;
- Atlas-связи, иконки, responsive/accessibility, edge states;
- legacy-отображение существующих offers и магазинов;
- тесты, ручная QA-матрица и handoff Session 2.5.

### Не входит и не должно быть начато

- изменение `offers` для обязательной ссылки на release/SKU;
- новая коммерческая модель объёма/цены;
- seller/admin workflow релизо-осознанных предложений;
- миграция legacy offers на release/SKU;
- публикация версии `1.1.0`.

До Session 2.6 переключение выпуска не обещает отфильтровать цены по точному SKU.
UI не должен создавать ложную связь между выбранным релизом и legacy-offer.

## 6. План реализации

### Этап 0. Baseline дизайна и документации

Результат:

- финальный полный визуальный мастер;
- production-ready icon kit и registry;
- настоящая поэтапная схема реализации;
- отдельный коммит до изменений Flutter/БД.

Критерий выхода: рабочее дерево после коммита чистое; владелец подтвердил этот
план или внёс правки. До подтверждения этап 1 не начинается.

### Этап 1. Read model карточки и выбор релиза

Статус: **release foundation и read path structured awards реализованы;
production-миграция knowledge tables применена и верифицирована 30.07.2026**.

Работы:

1. Добавить immutable `WineCardViewData` и provider family по `wineId`.
2. Подключить `wine_vintages`, `wine_vintage_images`, `wine_product_codes`,
   structured awards и Atlas terms одним координированным read flow.
3. Расширить `WineVintageRecord` нужными полями, включая grape composition и
   display metadata, без дублирования правил в UI.
4. Ввести `selectedReleaseId`; определить стабильный initial selection:
   публичный showcase/default release → подходящий актуальный → NV/последний
   допустимый → base-wine fallback.
5. Фильтровать служебные/pending/disabled записи на repository/provider boundary.
6. Оставить offers legacy и явно отделить их от выбранного release.

Автотесты:

- NV с `release_name`;
- два релиза одного года;
- pending/disabled не попадает в публичный selector;
- release override и base fallback для photo/description/ABV/grapes;
- отсутствие релизов;
- ошибка одного дополнительного источника не уничтожает всю карточку.

Контрольная точка: отдельный коммит `feat: add release-aware wine card read model`.

### Этап 2. Runtime assets, tokens и декомпозиция каркаса

Статус: **базовые tokens и верхние секции реализованы; декомпозиция нижних
секций продолжается по соответствующим этапам**.

Работы:

1. Использовать уже проверенные SVG из `assets/icons/wine_card/` через общий
   `WineCardIcon`; прямой вызов `SvgPicture.asset` в секциях не допускается.
2. Сохранять собственные цвета медалей, монохромным иконкам всегда передавать
   явный gold/green-gold `ColorFilter`.
3. Ввести `WineCardTokens`: фон, surface, золото, ruby accent, границы, радиусы,
   spacing, типографика и duration curves.
4. Вынести секции из монолита, пока сохраняя текущую визуальную семантику и
   callback-и. Не менять одновременно каркас и все данные.

Автотесты:

- все registry keys резолвятся в существующий asset;
- каждая секция рендерится отдельно;
- route, share, favorite, moderator actions и bottom CTA не потеряны.

Контрольная точка: отдельный коммит `refactor: split wine card into sections`.
