## 1. Почему это ТЗ отличается от стартового промпта

Стартовый промпт 29.07.2026 предполагал большой унаследованный массив предложений,
который надо аккуратно мигрировать: additive-схема, nullable FK, идемпотентный
backfill, очередь unresolved, compatibility period, legacy fallback.

Аудит живой базы 07.08.2026 этого не подтвердил.

### 1.1. Фактическое состояние продавцового контура

| Сущность | В production |
|---|---|
| `offers` | **2 строки**, оба — тестовые, одно вино «Мерло», 999 ₽, создано 15.03.2026 |
| `businesses` | 5: `Продавец-1`, `Продавец-2`, `Тестовый Официальный Магазин`, `XXX`, `GGG` |
| `locations` | **0** |
| `orders` / `order_items` / `cart_items` | **0 / 0 / 0** |
| профили `seller` | 4, все тестовые |

Реальные цены в продукте приходят не отсюда: `user_prices` — 100 строк,
`user_receipt_items` — 266. Вьюха `public_wine_price_summary` отдаёт
`display_price_source = 'receipt'` для 42 вин, `'none'` для 1201 и `'offer'` ровно
для одного — того самого тестового.

**Следствие:** мигрировать нечего. Backfill, legacy fallback, compatibility period
и очередь unresolved из стартового промпта не выполняются — не потому что решено
сэкономить, а потому что для них нет входных данных. Схема пересобирается сразу
в целевом виде.

### 1.2. Почему SKU не может жить в `wine_product_codes`

Стартовый промпт требовал переиспользовать `wine_product_codes` и не создавать
параллельную сущность SKU. Замысел таблицы это допускал — в ней есть
`bottle_volume_ml`, `package_kind`, `market_country_code`, `wine_vintage_id`,
а комментарий миграции `20260718` говорит «identifiers of a wine **or optional
concrete release/packaging**».

Но её первичная сущность — код:

```sql
code            text not null,
normalized_code text not null,
constraint wine_product_codes_normalized_digits_check
  check (normalized_code ~ '^[0-9]{4,32}$')
```

Строки без штрихкода в ней не существует. А товарная позиция без известного GTIN —
норма: магазин выставляет 0,75 л выпуска 2022, кода в базе нет. Обратное тоже
верно: у одной позиции бывает несколько кодов (`market_country_code` это прямо
допускает), а один код по правилам Session 2 может относиться к нескольким
выпускам одного вина.

**Позиция и штрихкод связаны как многие-ко-многим.** Сейчас упаковка
денормализована внутрь строки кода, и ничто в схеме не мешает двум кодам одной
бутылки разойтись по `bottle_volume_ml`.

Фактическое заполнение подтверждает, что как реестр товаров таблица не
использовалась: из 1076 кодов `bottle_volume_ml` заполнен у **3**,
`package_kind` — у **0**, `wine_vintage_id` — у 27; 1049 различных вин;
88 в статусе `conflicted`.

Поэтому вводится `wine_skus` — не параллельная система, а недостающее звено,
на которое эти колонки уже указывают.

### 1.3. Проверка на будущей интеграции с учётными системами

Учётная система магазина (1С, кассовое ПО, складской модуль) по одной позиции
отдаёт: **штрихкод, свой артикул, цену, остаток**.

Со слоем SKU разбор однозначен:

```
GTIN → wine_product_codes → wine_sku_id → upsert offers (цена, наличие)
```

Без слоя SKU штрихкод разрешается максимум в вино, и позиции 0,75 л и 1,5 л
одного магазина схлопываются в один объект. Импорт становится неоднозначным
по устройству модели, а не по недосмотру реализации.

Поэтому в этой сессии закладываются, но не используются: `offers.external_ref`,
`offers.source`, `locations.external_ref` и уникальность активного предложения
по паре «точка + SKU», которая превращает выгрузку в идемпотентный upsert.

под обоих потребителей сразу**, а не под конкретный админский экран.

## 3. Целевая модель

```
wines
  └─ wine_vintages          выпуск: год/NV, фото, описание, ABV   (есть, 30 строк)
       └─ wine_skus         + объём + упаковка = товарная позиция  (новое)
            ├─ wine_product_codes.wine_sku_id   коды позиции       (доработка)
            └─ offers       продавец, точка, цена, наличие         (пересборка)
                 └─ locations  конкретная торговая точка            (доработка)
                      └─ businesses  продавец / сеть                (есть)
```

Инварианты:

1. Предложение всегда указывает на **один** выпуск, **одну** позицию, **одну** точку.
2. Объём и упаковка живут только в `wine_skus`. В `offers` их нет.
3. Год, ABV и фото живут только в `wine_vintages`. В `offers` и `wine_skus` их нет.
4. Цена, валюта, наличие, актуальность — свойства предложения, и только его.
5. Активное предложение уникально по паре «точка + позиция».

## 4. Схема: `wine_skus`

```sql
create table public.wine_skus (
  id                 uuid primary key default gen_random_uuid(),
  wine_id            uuid not null references public.wines(id) on delete cascade,
  wine_vintage_id    uuid not null references public.wine_vintages(id) on delete cascade,
  bottle_size_id     uuid not null references public.bottle_sizes(id),
  package_kind       text not null default 'bottle',
  status             text not null default 'active',
  merged_into_sku_id uuid references public.wine_skus(id),
  created_at         timestamptz not null default timezone('utc', now()),
  updated_at         timestamptz not null default timezone('utc', now()),
  constraint wine_skus_package_kind_check check (
    package_kind in ('bottle', 'gift_box', 'can', 'bag_in_box', 'keg', 'other')
  ),
  constraint wine_skus_status_check check (
    status in ('active', 'archived', 'merged')
  ),
  constraint wine_skus_merge_target_check check (
    (status = 'merged') = (merged_into_sku_id is not null)
  )
);

create unique index wine_skus_identity_unique
  on public.wine_skus(wine_vintage_id, bottle_size_id, package_kind)
  where status = 'active';

create index wine_skus_wine_idx on public.wine_skus(wine_id, status);
```

`wine_id` денормализован для запросов уровня вина. Согласованность с
`wine_vintages.wine_id` держит триггер — тем же приёмом, что
`validate_wine_product_code_vintage` в миграции `20260718`.

`merged_into_sku_id` нужен потому, что объединение вин уже существует
(`admin_merge_wines`) и после слияния двух вин их позиции могут совпасть.

### 4.1. Единственная точка записи

```sql
public.resolve_wine_sku(
  p_wine_vintage_id uuid,
  p_bottle_size_id  uuid,
  p_package_kind    text default 'bottle'
) returns uuid
```

`security definer`, `set search_path = public`. Get-or-create: возвращает id
существующей активной позиции либо создаёт новую. Идемпотентна.

Право вызова — администратор каталога либо владелец любого бизнеса
(последнее нужно будущему кабинету продавца). Прямой `INSERT` в `wine_skus`
закрыт RLS для всех, кроме администратора.

Модерация для позиций не вводится: тройка «выпуск + объём + упаковка» —
объективный факт, в отличие от года выпуска, который является утверждением
о мире. Администратору достаточно объединения и архивации.

### 4.2. Связь с кодами

```sql
alter table public.wine_product_codes
  add column wine_sku_id uuid references public.wine_skus(id) on delete set null;

create index wine_product_codes_sku_idx
  on public.wine_product_codes(wine_sku_id) where wine_sku_id is not null;
```

Backfill не делается: `bottle_volume_ml` заполнен у 3 строк из 1076, выводить
позицию не из чего. Колонка заполняется по мере уточнения кодов вручную и
будущим импортом. `bottle_volume_ml`/`package_kind` в таблице кодов остаются
как есть и не удаляются — они становятся сырьём для определения позиции.

## 5. Схема: `locations`

Таблица существует с марта 2026, содержит 0 строк, не имеет ни одной входящей
ссылки и не создаётся ни из одного экрана — только читается карточкой бизнеса
в админке. Права уже корректны: владелец бизнеса и администратор каталога.

### 5.1. Что добавляется

```sql
alter table public.locations
  add column name              text,
  add column is_retail_active  boolean not null default false,
  add column is_active         boolean not null default true,
  add column closed_at         timestamptz,
  add column external_ref      text,
  add column city              text,
  add column country_code      text references public.countries(code) on delete set null,
  add column geocode_status    text not null default 'pending',
  add column geocoded_at       timestamptz;
```

| Колонка | Зачем |
|---|---|
| `name` | «Пятёрочка» — бизнес, «Пятёрочка на Ленина, 5» — точка. Без имени список сети нечитаем |
| `is_retail_active` | Явный признак «здесь продают». Симметричен существующему `is_tourism_active`. Позволяет выключить торговлю на точке, не удаляя её |
| `is_active` / `closed_at` | Точку нельзя удалять — на неё ссылаются предложения. Закрытие вместо удаления |
| `external_ref` | Код точки в учётной системе магазина. Без него выгрузку не привязать |
| `city`, `country_code` | Фильтр «в моём городе». Заполняется геокодером |
| `geocode_status`, `geocoded_at` | Без координат точки нет на карте; статус нужен, чтобы видеть неразобранные адреса |

Ограничения и индексы:

```sql
alter table public.locations
  add constraint locations_name_not_blank
    check (name is null or btrim(name) <> ''),
  add constraint locations_geocode_status_check
    check (geocode_status in ('pending', 'ok', 'failed', 'manual')),
  add constraint locations_closed_at_check
    check ((is_active = false) or closed_at is null);

create unique index locations_business_external_ref_unique
  on public.locations(business_id, external_ref)
  where external_ref is not null;

create index locations_business_idx on public.locations(business_id, is_active);
create index locations_retail_idx
  on public.locations(is_retail_active) where is_retail_active and is_active;
```

Уникальность по адресу **не вводится**: два магазина в одном торговом центре —
законный случай. Совпадение адреса внутри бизнеса показывается в форме как
предупреждение, а не как блокировка.

### 5.2. Права на чтение

Текущая политика — `Authenticated users can read locations` с условием
`auth.uid() is not null`. Карточка вина у гостя сейчас работает только потому,
что `get_wine_purchase_places` объявлена `security definer` и обходит RLS.

Добавляется публичная политика на активные торговые точки:

```sql
create policy "Anyone can view active retail locations"
on public.locations for select
using (is_active = true and is_retail_active = true);
```

Существующая политика для аутентифицированных остаётся — она даёт доступ
к нерозничным точкам (склады, дегустационные залы) владельцу и админу.

### 5.3. Геокодирование

Переиспользуется существующая edge-функция
[`geocode-receipt`](../supabase/functions/geocode-receipt/index.ts) (Яндекс),
обобщённая до произвольного адреса. Второй геокодер не заводится.

Из ответа берутся `latitude`, `longitude`, `city`, `country_code`,
проставляется `geocode_status`. Ручной ввод координат ставит `manual`
и не перетирается автоматикой.

**Экономия обращений.** Замер 07.08.2026 показал 84 обращения к геокодеру
на 17 уникальных адресов: защита стояла на уровне отдельного чека
(`lat is null`), а не на уровне адреса, поэтому один и тот же адрес магазина
разбирался заново каждым новым чеком. Дело не только в деньгах —
у Яндекса бесплатный доступ обусловлен соблюдением условий, и ключи
блокируют за нарушения.

Три уровня защиты, все проверены на живой функции:

| Ситуация | Поведение | Обращение к провайдеру |
|---|---|---|
| У записи уже есть координаты | `skipped: already_geocoded` | нет |
| Адрес встречался раньше | Ответ из `geocode_cache` | нет |
| Адрес новый | Яндекс, затем Photon; результат в кэш | одно |
| Провайдер не нашёл адрес | Отрицательный ответ кэшируется на 30 дней | одно, затем нет |

Кэш держится на `normalize_place_address`. Проверено на семи написаниях
одного адреса — шесть схлопываются в один ключ `31 крым пушкинская ялта`:

| Что различалось | Создаёт ли новое обращение |
|---|---|
| Запятые, точки, регистр | нет |
| Порядок слов (`Ялта г, Пушкинская ул` против `г. Ялта, ул. Пушкинская`) | нет |
| Сокращения `г.о.`, `г.`, `Респ.`, `Республика`, `ул.`, `д.`, `дом` | нет |
| Почтовый индекс | нет |
| Лишняя «Россия» | нет |
| **Пропущенная смысловая часть** (`Ялта, Пушкинская, 31` без «Крым») | **да** |

Последний случай при ручном вводе в админке будет встречаться постоянно,
поэтому перед обращением к провайдеру делается вторая попытка — поиск
похожего адреса среди уже разобранных, через `pg_trgm`.

Защита от ложного совпадения: **номера домов обязаны совпадать**. Без этого
`Пушкинская 31` и `Пушкинская 12Б` слились бы в одну точку, а по чекам видно,
что это два разных магазина. Проверено: `Пушкинская 12` без литеры и
несуществующий `Пушкинская 99` не находятся ничем; `12А` и `12Б` остаются
раздельными записями, хотя стоят в одном здании и делят координаты.

Ответ функции содержит `cache_match`: `exact` — совпал ключ, `fuzzy` — нашёлся
похожий адрес, отсутствует — обращались к провайдеру.

**Принудительное обновление.** Координаты можно переразобрать в любой момент —
параметр `force: true` обходит и кэш, и проверку уже известных координат,
обращается к провайдеру и обновляет запись кэша. Нужен, когда адрес исправили,
когда геокодер раньше ошибся или когда точка переехала. В админке — кнопка
`Обновить координаты` рядом с адресом точки; массового автоматического
переразбора нет и быть не должно.

### 5.4. Вывеска и юридическое имя

Название в чеке — почти всегда юридическое лицо, а не то, что человек видит
на фасаде. Выборка из 87 чеков production не оставляет в этом сомнений:

| В чеке | Что видит человек |
|---|---|
| `ООО "Агроторг"`, ИНН 7825706086 | Пятёрочка |
| `АКЦИОНЕРНОЕ ОБЩЕСТВО "ТАНДЕР"`, ИНН 2310031475 | Магнит |
| `ОБЩЕСТВО С ОГРАНИЧЕННОЙ ОТВЕТСТВЕННОСТЬЮ "АЛЬФА-М"`, ИНН 7743931676 | Красное & Белое |
| `ООО"Лента"`, ИНН 7814148471 | Лента |

Поэтому у продавца разделяются две сущности имени:

```sql
alter table public.businesses
  add column legal_name text;   -- «ООО "Агроторг"», как в реестре и в чеке
-- businesses.name остаётся вывеской: «Пятёрочка»
```

Правило показа: **везде в пользовательском интерфейсе — вывеска**. Юридическое
имя показывается вторичной строкой в карточке продавца и в истории чеков,
где человеку важно сопоставить с бумажкой. В карточке вина, на карте и в
«Где купить» юридического имени нет.

У точки `name` — это уточнение внутри сети (`на Пушкинской`, `ТЦ Конфетти`),
а не повтор бренда. Полное отображаемое имя собирается как
`businesses.name + ' · ' + locations.name`.

### 5.5. Мост между чековыми местами и точками магазинов

Требование владельца: адреса, которые подтягиваются при сканировании чеков,
и адреса точек магазинов не должны стать двумя независимыми сущностями.

**Ключ сопоставления уже есть в данных.** `user_receipts.shop_inn` заполнен
в **87 чеках из 87** — то есть в 100 % случаев, 12 различных ИНН. Это
надёжный идентификатор юридического лица, в отличие от названия, которое
приходит в разных написаниях (`ООО "Агроторг"` и полная форма — один и тот же
ИНН).

**Бренд — не продавец.** `businesses.owner_id` объявлен `not null`: бизнес
обязан иметь владельца-пользователя. Пятёрочка продавцом WinePool не является
и аккаунта не имеет, а вывеску показывать нужно. Поэтому справочник брендов
существует отдельно от продавцов и лишь необязательно с ними связывается:

```sql
create table public.retail_brands (
  id          uuid primary key default gen_random_uuid(),
  name        text not null,                                  -- «Пятёрочка»
  slug        text not null,
  logo_url    text,
  business_id uuid references public.businesses(id) on delete set null,
  status      text not null default 'active',
  created_at  timestamptz not null default timezone('utc', now()),
  updated_at  timestamptz not null default timezone('utc', now()),
  constraint retail_brands_name_not_blank check (btrim(name) <> ''),
  constraint retail_brands_status_check check (status in ('active', 'archived'))
);

create unique index retail_brands_slug_unique on public.retail_brands(slug);

create table public.retail_brand_legal_entities (
  id         uuid primary key default gen_random_uuid(),
  brand_id   uuid not null references public.retail_brands(id) on delete cascade,
  inn        text not null,
  legal_name text,
  is_primary boolean not null default false,
  created_at timestamptz not null default timezone('utc', now()),
  constraint retail_brand_legal_entities_inn_check check (inn ~ '^[0-9]{9,12}$')
);

create unique index retail_brand_legal_entities_inn_unique
  on public.retail_brand_legal_entities(inn);
create index retail_brand_legal_entities_brand_idx
  on public.retail_brand_legal_entities(brand_id);
```

ИНН глобально уникален: одно юрлицо не может принадлежать двум брендам.

`business_id` заполняется, только если бренд стал настоящим продавцом
WinePool. Пустое значение — нормальное состояние: `Пятёрочка` живёт в
справочнике как вывеска для чеков и без единого предложения.

Чтение `retail_brands` публичное — вывеску должен видеть гость. Запись —
только администратор каталога.

**Сопоставление конкретной точки.** Один ИНН — много точек. Данные это прямо
показывают: ИНН 9103012413 приходит с двух адресов, `ул. Пушкинская, д. 31`
и `ул. Пушкинская, зд. 12Б`, — это два разных магазина одной сети.

```sql
public.match_receipt_place_to_location(
  p_inn     text,
  p_lat     double precision,
  p_lng     double precision,
  p_address text default null
) returns uuid
```

Логика: ИНН → `retail_brand_legal_entities` → бренд → связанный продавец
(если есть) → его активные торговые точки → ближайшая в радиусе
**150 метров**. Если координат нет — сравнение нормализованного адреса.
Неоднозначность не разрешается угадыванием: функция возвращает `null`,
и наблюдение остаётся чековым.

```sql
alter table public.user_receipts
  add column matched_brand_id    uuid references public.retail_brands(id) on delete set null,
  add column matched_location_id uuid references public.locations(id) on delete set null,
  add column matched_at timestamptz;
```

Две ссылки, а не одна, потому что это два независимых уровня успеха:

- **бренд определён, точка нет** — самый частый случай. Чек показывает
  `Пятёрочка` вместо `ООО "Агроторг"`, и одного этого уже достаточно, чтобы
  человек узнал свой магазин;
- **определены оба** — чековое наблюдение схлопывается с предложением
  магазина в один пин на карте.

Заполняется при разборе нового чека и разовым идемпотентным проходом по
существующим 87. Не меняет ни одного существующего поля чека — исходные
`shop_name`, `shop_address`, `shop_inn` сохраняются как есть, в соответствии
с принципом «raw не теряется» из
[`my_places_user_shops_tz_2026_06_13.md`](my_places_user_shops_tz_2026_06_13.md).

**Что это даёт в карточке вина.** Сегодня чековое наблюдение и предложение
того же магазина — два независимых пина. После сопоставления они схлопываются
в одну точку: `Пятёрочка на Нансена, 103 · 1 190 ₽ от магазина · 4 покупки
по чекам`. Именно это и означает «не две разные сущности».

**Найденный попутно дефект.** Существующий `user_receipts.shop_geo_key` имеет
вид `общество|44.4975|34.1711` — первым сегментом берётся первое слово
юридического названия, а все ООО начинаются со слова «ОБЩЕСТВО». Ключ
фактически вырождается в координаты, и два разных магазина в одном здании
схлопнутся в один. После введения сопоставления по ИНН этот ключ перестаёт
быть несущим; переписывать его в этой сессии не требуется, но полагаться
на него нельзя.

### 5.6. Откуда берётся вывеска: разбор вариантов

Вопрос владельца 07.08.2026: можно ли по ИНН автоматически понять, что
`ООО "Агроторг"` — это Пятёрочка. Проверено по источникам, ответ отрицательный.

| Источник | Что даёт | Почему не решает |
|---|---|---|
| ФНС / ЕГРЮЛ, [api-fns.ru](https://api-fns.ru/) | Юр. название, адрес регистрации, ОКВЭД, руководитель | Вывеска не является реестровым фактом. Реестра «ИНН → бренд» не существует |
| [DaData](https://dadata.ru/api/find-party/) | То же самое, удобным API. Бесплатно 10 000 запросов/день, платно от 14 000 ₽/год | Тот же реестр — бренда в нём нет |
| [Яндекс Поиск по организациям](https://yandex.ru/dev/maps/geosearch/) | По координатам вернёт «Пятёрочка, супермаркет». Бесплатно до 500 запросов/день | **Лицензия запрещает сохранять результаты** — только показ на карте. Расширенной лицензии с правом сохранения не существует. Путь закрыт юридически |
| Роспатент / ФИПС | Товарные знаки: «Агроторг» владеет знаком «Пятёрочка» | У крупных сетей десятки знаков, сопоставление шумное. Много ручного труда, ненадёжный результат |

**Принятое решение — ручной справочник.** Это не компромисс, а решение по
масштабу: 12 ИНН покрывают все 87 чеков production целиком, два-три десятка
накроют практически весь винный ритейл РФ. Юрлица у сетей меняются редко,
справочник почти не стареет.

Справочник — это и есть `business_legal_entities` из §5.5: заводя продавца,
администратор указывает вывеску и один или несколько ИНН.

**DaData подключается, но для другой задачи** — автозаполнение `legal_name`
и проверка, что ИНН существует, при вводе в админке. Бесплатного тарифа
хватает с многократным запасом. Это удобство ввода, а не источник вывески.

**Краудсорсинг вывески — отдельным слайсом позже.** Пользователь видит в
истории чеков `ООО "Агроторг"` и кнопку **«Уточнить название магазина»** —
формулировка описывает действие и не обвиняет систему в ошибке. Предложенная
вывеска идёт в существующую модерацию.

Ценность масштабная: ИНН один на всю сеть, поэтому одно принятое уточнение
переименовывает магазины бренда **во всех городах сразу**.

В Session 2.6 не входит намеренно. Слайс сам по себе небольшой — форма
в истории чеков плюс очередь в модерации, — но осмысленным становится только
после заполнения ручного справочника: пока он пуст, модератор будет разбирать
предложения по брендам, которые и так собирался завести. Схема (`retail_brands`
и `retail_brand_legal_entities` из §5.5) готовится в этой сессии, поэтому
позже потребуется добавить форму, а не переделывать модель.

### 5.7. Связь с разделом «Мои места»

[`my_places_user_shops_tz_2026_06_13.md`](my_places_user_shops_tz_2026_06_13.md)
описывает приватное переименование юридического имени в вывеску силами самого
пользователя и оставляет открытым вопрос «место — это бренд или конкретная
точка».

Session 2.6 отвечает на этот вопрос на уровне каталога: **место — конкретная
точка, бренд — бизнес**. И снимает бо́льшую часть потребности в приватном
переименовании: как только ИНН сопоставлен с продавцом, пользователь видит
вывеску из каталога автоматически, без ручного труда. «Мои места» остаётся
нужным для магазинов, которых в каталоге нет, — и реализуется отдельным
слайсом поверх уже готового сопоставления.

## 6. Схема: пересборка `offers`

### 6.1. Что есть сейчас

```
id, seller_id, price, created_at, updated_at, wine_id,
vintage, is_active, bottle_size_id, business_id
```

Ни одного индекса кроме первичного ключа. Девять наслоившихся RLS-политик.

### 6.2. Дыра в правах, которую закрывает эта сессия

Среди девяти политик рядом с корректной

```sql
"Owners can insert modern offers"
  with check (seller_id = auth.uid()
              and business_id is not null
              and is_business_owner(business_id, auth.uid()))
```

живёт унаследованная

```sql
"Sellers can create their own offers"
  with check (auth.uid() = seller_id)
```

Политики складываются по ИЛИ. **Любой аутентифицированный пользователь может
вставить себе предложение напрямую через PostgREST.** Роль продавца проверяется
только на клиенте — [`router.dart:1090`](../lib/core/router.dart#L1090),
`capabilities.canAccessSellerHome`. База не проверяет ничего.

Это не гипотетический риск: цена из предложения имеет приоритет над чековой
в `public_wine_price_summary`, то есть подставленная строка перебивает реальную
статистику вина. Закрывается в этой сессии независимо от остального объёма.

### 6.3. Целевая структура

Тестовые строки удаляются (`cart_items` и `order_items` пусты, каскадных
последствий нет), после чего колонки добавляются сразу как `not null`.

```sql
delete from public.offers;

alter table public.offers
  add column wine_sku_id      uuid not null references public.wine_skus(id),
  add column location_id      uuid not null references public.locations(id),
  add column currency_code    text not null default 'RUB',
  add column is_available     boolean not null default true,
  add column stock_quantity   integer,
  add column external_ref     text,
  add column source           text not null default 'manual',
  add column price_updated_at timestamptz not null default timezone('utc', now()),
  add column valid_until      timestamptz,
  add column created_by       uuid references public.profiles(id),
  add column updated_by       uuid references public.profiles(id);

alter table public.offers
  drop column vintage,
  drop column bottle_size_id;
```

`wine_id` и `business_id` остаются денормализованными: первый — для запросов
уровня вина, второй — потому что на него опирается `is_business_owner` в RLS.
Согласованность с `wine_skus.wine_id` и `locations.business_id` держит триггер.

`seller_id` остаётся как автор записи.

```sql
alter table public.offers
  add constraint offers_source_check
    check (source in ('manual', 'import', 'api')),
  add constraint offers_currency_check
    check (currency_code ~ '^[A-Z]{3}$'),
  add constraint offers_stock_check
    check (stock_quantity is null or stock_quantity >= 0);

create unique index offers_active_location_sku_unique
  on public.offers(location_id, wine_sku_id) where is_active;

create unique index offers_external_ref_unique
  on public.offers(location_id, external_ref) where external_ref is not null;

create index offers_sku_idx      on public.offers(wine_sku_id) where is_active;
create index offers_location_idx on public.offers(location_id)  where is_active;
create index offers_wine_idx     on public.offers(wine_id)      where is_active;
```

`offers_active_location_sku_unique` — центральное ограничение сессии. Оно даёт
и защиту от дублей, и ключ идемпотентного upsert для будущего импорта.

### 6.4. Права

Все девять политик удаляются, создаются четыре:

```sql
create policy "Anyone can view active offers"
on public.offers for select using (is_active = true);

create policy "Owners and admins can insert offers"
on public.offers for insert with check (
  is_catalog_admin(auth.uid())
  or (business_id is not null and is_business_owner(business_id, auth.uid()))
);
-- аналогично для update и delete
```

Публичное чтение активных предложений обязательно: цены должен видеть гость.

### 6.5. Запись

```sql
public.upsert_offer(
  p_wine_sku_id    uuid,
  p_location_ids   uuid[],
  p_price          numeric,
  p_currency_code  text default 'RUB',
  p_is_available   boolean default true,
  p_stock_quantity integer default null,
  p_valid_until    timestamptz default null,
  p_external_ref   text default null,
  p_source         text default 'manual'
) returns setof public.offers
```

`p_location_ids` — массив с самого начала, хотя UI 1.1.0 передаёт одну точку.
Это то, что позволит кабинету продавца добавить массовый ввод по сети без
переделки бэкенда (решение 7).

Функция проверяет: вызывающий — администратор либо владелец бизнеса каждой
переданной точки; точка активна и `is_retail_active`; позиция активна.
Обновляет существующую активную строку по паре «точка + позиция» либо создаёт
новую. При изменении цены двигает `price_updated_at`.

Все изменяющие действия пишутся в существующий аудит-контур.

## 7. Чтение: `get_wine_purchase_places`

### 7.1. Что функция делает сейчас

Объединяет два источника — предложения магазинов и наблюдения из чеков — и
ставит предложения выше чеков в сортировке. Секция «Где купить» в карточке вина
([`wine_purchase_places_section.dart`](../lib/features/wines/presentation/wine_details/wine_purchase_places_section.dart))
на это уже рассчитана и переписыванию не подлежит.

Два дефекта относительно целей 2.6:

1. **Группировка по бизнесу**, а не по точке: `place_key = 'offer:' || business.id`.
2. **Адрес берётся «любой первый»** — боковой `lateral`-подзапрос выбирает
   первую попавшуюся точку бизнеса, предпочитая `retail_shop`. При сети из
   сорока магазинов карта показывает один пин в случайном месте.
3. Фильтра по выпуску и объёму нет вовсе.

### 7.2. Целевое поведение

Сигнатура расширяется параметрами со значениями по умолчанию — это сохраняет
работоспособность уже опубликованных APK во время staged rollout 1.1.0:

```sql
public.get_wine_purchase_places(
  p_wine_id         uuid,
  p_wine_vintage_id uuid default null,
  p_wine_sku_id     uuid default null,
  p_user_lat        double precision default null,
  p_user_lng        double precision default null
)
```

Существующий состав возвращаемых колонок сохраняется целиком, новые
добавляются в конец — старый клиент лишние поля игнорирует, а переименование
или удаление колонки его бы сломало.

Изменения:

- `place_key = 'offer:' || location.id`, группировка по точке;
- `place_name` — имя точки, плюс новая колонка с именем бизнеса для свёртки;
- координаты и адрес — самой точки, без `lateral`-угадывания;
- новые колонки: `location_id`, `business_name`, `wine_sku_id`,
  `bottle_size_ml`, `package_kind`, `is_available`, `price_updated_at`;
- при заданном `p_wine_vintage_id` предложения фильтруются по выпуску;
  при заданном `p_wine_sku_id` — по конкретной позиции;
- чековые наблюдения остаются как есть и по выпуску не фильтруются —
  чек не знает выпуска. При выбранном выпуске они помечаются как относящиеся
  к вину в целом;
- чековые наблюдения с заполненным `matched_location_id` (§5.5) сливаются
  с предложением той же точки в один результат, а не образуют второй пин.

### 7.3. Расстояние до точки

Владелец разрешения на геолокацию сейчас не запрашивает. Модель строится так,
чтобы включение геолокации позже не потребовало переделки сервера.

При переданных `p_user_lat`/`p_user_lng` функция добавляет колонку
`distance_m` и допускает сортировку по возрастанию расстояния. Без координат
колонка равна `null`, порядок остаётся прежним — предложения выше чеков,
затем по цене.

**PostGIS в базе не установлен** (расширений `postgis`, `cube`, `earthdistance`
нет — проверено 07.08.2026). Поэтому:

- расстояние считается формулой гаверсинуса прямо в SQL;
- предварительное отсечение — прямоугольником по широте и долготе, чтобы
  тригонометрия применялась не ко всем строкам;
- индекс `locations(latitude, longitude) where is_active and is_retail_active`.

При десятках тысяч точек этого хватит. Переход на PostGIS — отдельное решение,
и вводить расширение ради одной сортировки сейчас не нужно.

**Координаты пользователя не сохраняются** — ни в таблицу, ни в лог. Они
живут только как параметры запроса. Это осознанное требование 152-ФЗ:
местоположение относится к персональным данным, и хранить его без отдельного
согласия нельзя.

## 8. Пользовательский опыт

### 8.1. Карточка вина

**Объёмы — отдельные варианты.** Внутри выбранного выпуска показываются
доступные позиции с собственными ценами: `0,75 л · от 1 190 ₽`,
`1,5 л · от 2 340 ₽`. Переключение объёма меняет список магазинов и цену
целиком, без переноса данных предыдущего выбора.

**Свёртка по сети.** Если у бизнеса несколько точек с этим товаром, в списке
одна строка: `Пятёрочка · от 1 190 ₽ · 12 магазинов`, разворачивается по тапу.
На карте — все точки, каждая со своей ценой. Без свёртки список превращается
в сорок одинаковых строк.

**Смена выпуска.** Цена, магазины и наличие пересчитываются явно. Показывать
цену другого выпуска как цену выбранного запрещено.

**Уровень вина без выбранного выпуска.** Допускается агрегированный диапазон
по всем выпускам с прозрачной подписью, из которой видно, что это диапазон,
а не цена конкретной бутылки.

**Имена.** В списке и на карте — вывеска плюс уточнение точки:
`Пятёрочка · на Нансена, 103`. Юридическое имя в карточке вина не появляется
(§5.4).

**Граничные случаи, обязательные к обработке:** цены нет; одна цена; несколько
магазинов; несколько объёмов; выпуск архивный; позиция архивная; предложение
просрочено по `valid_until`; товара нет в наличии (`is_available = false`);
есть только чековые наблюдения; нет ничего.

### 8.1.1. Расстояние и маршрут

Решение владельца 07.08.2026: функциональность делается **полностью и сразу**,
включая клиент, но выдаётся по флагу — сначала администраторам и модераторам.
Так её можно отладить на живых данных задолго до открытия всем, а включение
станет решением в админке, а не новым релизным циклом.

- При известных координатах у каждой точки — расстояние человеческим
  форматированием: `340 м`, `1,2 км`, `18 км`. Список магазинов получает
  переключатель порядка «по цене / по расстоянию».
- **Маршрут не строим внутри приложения.** Кнопка `Маршрут` открывает
  внешнюю карту по deeplink с фолбэком на веб-ссылку. Своя навигация поверх
  MapKit — отдельный продукт, и не наш.
- Точка без координат остаётся в списке без расстояния и без кнопки маршрута,
  а не исчезает.
- **Системный запрос разрешения поднимается только при активном для этой роли
  флаге.** Обычный пользователь в 1.1.0 диалога не увидит: незапрошенное
  разрешение раздражает людей и плохо смотрится при проверке в сторах.
  Если доступ уже выдан по другому сценарию — координаты используются.

### 8.1.2. Флаги функциональности

Механизма флагов в проекте нет — есть только `app_release_config`. Вводится
минимальная таблица:

```sql
create table public.app_feature_flags (
  key                text primary key,
  description        text,
  is_enabled_for_all boolean not null default false,
  enabled_for_roles  text[] not null default '{}',
  updated_at         timestamptz not null default timezone('utc', now()),
  updated_by         uuid references public.profiles(id)
);
```

Чтение публичное, запись — только администратор каталога. Первый флаг —
`nearby_places_distance`, включённый для ролей `administrator` и `moderator`.

Открытие функции всем — это `UPDATE` одной строки, без пересборки APK.
Именно это делает возможным «ввести в ближайшие релизы» без релизного цикла.

Серверная часть (`distance_m` и сортировка) флагом не закрывается — она
безвредна и при выключенном клиенте просто не используется.

### 8.2. Админка (базовый уровень, 1.1.0)

**Продавец.** В карточке бизнеса — вывеска (`name`), юридическое имя
(`legal_name`) и список юрлиц с ИНН (§5.5). Добавление ИНН сразу показывает,
сколько чековых наблюдений к нему привязалось, — это делает связь видимой,
а не молчаливой.

**Точки бизнеса.** В карточке бизнеса — создание, редактирование, закрытие
точки: имя, тип, адрес с геокодированием, город, телефон, почта,
`is_retail_active`, `external_ref`. Сейчас там только список без действий.
Рядом с точкой — число сопоставленных чековых наблюдений и кнопка
пересопоставления.

**Предложения.** Отдельный раздел: выбор вина → выпуска → объёма и упаковки →
точки → цены, валюты, наличия и срока актуальности. Сохранение невозможно,
пока выпуск и позиция не определены однозначно — это гарантируется схемой,
а форма лишь не даёт дойти до ошибки.

**Нет нужного выпуска.** Кнопка ведёт в существующий контур модерации:
`create_wine_release_proposal`, тип заявки `new_release_for_existing_wine`
(миграция [`20260720_add_user_wine_release_proposals.sql`](../supabase/migrations/20260720_add_user_wine_release_proposals.sql)).
Новый модерационный контур не строится.

**Список предложений** с фильтрами по бизнесу, точке и вину, с пометкой
просроченных по `valid_until`.

### 8.3. Кабинет продавца — не в этой сессии

Экраны `Добавить предложение` и `Изменить предложение` в мобильном приложении
работают по старой модели и после пересборки схемы станут нерабочими.
В 1.1.0 они **скрываются**, а не переписываются: маршруты `/add-offer` и
`/edit-offer` возвращают заглушку «Управление предложениями скоро появится
в кабинете продавца». Роль `seller` при этом сохраняется и права в базе
остаются валидными — кабинет подключится к готовым RPC.

## 10. Проверка

### 10.1. Автоматические тесты

**Схема и права:**
- гость читает активные предложения и активные торговые точки;
- обычный аутентифицированный пользователь **не может** вставить предложение —
  прямая проверка закрытия дыры из §6.2;
- владелец бизнеса пишет только в свои точки;
- администратор пишет везде;
- вторая активная строка по паре «точка + позиция» отвергается;
- `wine_id` в предложении, не совпадающий с вином позиции, отвергается;
- `business_id`, не совпадающий с бизнесом точки, отвергается.

**RPC:**
- `resolve_wine_sku` идемпотентна: два вызова с одинаковой тройкой возвращают
  один id;
- `resolve_wine_sku` не создаёт дубль после архивации и повторного обращения;
- `upsert_offer` со списком из N точек создаёт ровно N строк;
- повторный `upsert_offer` обновляет, а не дублирует;
- `upsert_offer` отвергает точку чужого бизнеса и нерозничную точку;
- `get_wine_purchase_places` без параметров возвращает тот же состав колонок,
  что и раньше, — проверка совместимости со старым клиентом;
- `get_wine_purchase_places` с выпуском не возвращает предложения других
  выпусков;
- `get_wine_purchase_places` с координатами возвращает `distance_m` и
  корректный порядок; без координат — `null` и прежний порядок;
- `match_receipt_place_to_location` находит точку по ИНН и координатам
  в радиусе 150 м;
- при двух точках одного ИНН в радиусе выбирается ближайшая, а при равном
  расстоянии возвращается `null`, а не произвольная;
- при неизвестном ИНН возвращается `null`;
- сопоставленное чековое наблюдение сливается с предложением той же точки
  в один результат, а не удваивает пин;
- `retail_brand_legal_entities`: один ИНН нельзя привязать к двум брендам;
- бренд без связанного продавца создаётся и читается гостем — проверка того,
  что `Пятёрочка` живёт в справочнике без аккаунта и без предложений;
- проход сопоставления идемпотентен — повторный запуск не меняет результат.

**UI:** выбор выпуска и объёма, пересчёт цены при смене того и другого,
свёртка по сети, все граничные случаи из §8.1.

## 11. Порядок работ

| # | Шаг | Результат |
|---|---|---|
| 1 | Миграция `locations` | Колонки, ограничения, индексы, публичная политика |
| 2 | Обобщение геокодера | Адрес точки → координаты, город, страна |
| 3 | `businesses.legal_name`, `retail_brands`, `retail_brand_legal_entities` | Вывеска отдельно от юрлица и отдельно от продавца (§5.4, §5.5) |
| 4 | Мост к чекам | `match_receipt_place_to_location`, `matched_brand_id`/`matched_location_id`, проход по 87 чекам (§5.5) |
| 5 | Миграция `wine_skus` + `resolve_wine_sku` | Позиция и единственная точка записи |
| 6 | `wine_product_codes.wine_sku_id` | Связь кодов с позицией, без backfill |
| 7 | Пересборка `offers` + RLS + `upsert_offer` | Целевая схема, закрытая дыра в правах |
| 8 | Переписать `get_wine_purchase_places` | Точка вместо бизнеса, выпуск, слияние с чеками, `distance_m` |
| 9 | Админка: продавец и точки | Юрлица с ИНН, CRUD точек |
| 10 | Админка: предложения | Форма и список |
| 11 | `app_feature_flags` | Флаг `nearby_places_distance` для админов и модераторов (§8.1.2) |
| 12 | Карточка вина | Объёмы, свёртка по сети, расстояние и маршрут за флагом, граничные случаи |
| 13 | Скрыть мобильные экраны предложений | Заглушка вместо нерабочей формы |
| 14 | Уборка §9 | Мёртвый код, тестовые данные, `get_wines_with_prices` |
| 15 | Тесты, QA-матрица, handoff | §10 |

Шаги 1–8 — серверные, проверяются на живой базе по протоколу из
[`powershell_ssh_sql_quoting_guide.md`](powershell_ssh_sql_quoting_guide.md):
backup, SHA-256, применение, post-check. После каждой миграции —
`NOTIFY pgrst, 'reload schema'`, иначе новые RPC не видны приложению.

Миграции несут собственные `begin/commit`, поэтому обёртка
`BEGIN … ROLLBACK` для сухого прогона не работает — проверка делается
встроенными `raise exception`.

## 12. Границы

Не входит в Session 2.6:

- оплата, корзина, оформление заказа, комиссии, логистика;
- полноценный кабинет продавца (архитектура закладывается, UI — нет);
- массовый ввод по сети в интерфейсе (RPC готов, UI — с кабинетом);
- импорт из 1С и внешние API (поля заложены, обмен не строится);
- разбор 1073 кодов без объёма и 88 конфликтующих — отдельная работа
  по качеству данных;
- открытие расстояния и маршрута обычным пользователям — функциональность
  готова целиком, но выдаётся по флагу админам и модераторам (§8.1.2);
- построение маршрута внутри приложения — только deeplink во внешнюю карту;
- краудсорсинг вывесок силами пользователей (§5.6) — отдельный слайс;
- автоматическое определение бренда по ИНН — источника не существует (§5.6);
- переход на PostGIS;
- переписывание `user_receipts.shop_geo_key` (дефект зафиксирован в §5.5);
- полный раздел «Мои места» с приватным переименованием — отдельный слайс
  поверх сопоставления из §5.5;
- Session 3 и пользовательский Copilot;
- изменение публичной иерархии карточки и политики фотографий, принятых
  в Session 2.5;
- удаление legacy-колонок за пределами `offers.vintage` и
  `offers.bottle_size_id`.

Сборка магазинных артефактов не делается: Android APK собирает владелец,
магазинные сборки готовятся после приёмки. Admin web можно собирать и
деплоить без дополнительного согласования.

Session 2.6 не считается принятой до ручной приёмки владельцем.
