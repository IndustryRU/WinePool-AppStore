# WinePool — стартовый промпт Session 2.6

Дата фиксации: 29.07.2026

Назначение: передать в отдельную задачу Codex реализацию Session 2.6 — предложения
магазинов, цены и доступность на уровне конкретного релиза и SKU. Начинать только
после завершённой и принятой владельцем Session 2.5.

## Готовый промпт

```text
Продолжаем WinePool в репозитории R:\Flutter\Project\winepool_final.

Нужно выполнить отдельную Session 2.6: «Релизо-осознанные предложения магазинов,
SKU, объёмы и цены». Это самостоятельная подсессия после принятой Session 2.5 и
перед публичным релизом 1.1.0. Пользовательский Copilot/Session 3 не входит.

Сначала полностью прочитай и сопоставь:
1. docs/catalog_search_copilot_four_session_execution_plan_2026_07_17.md;
2. docs/catalog_fast_search_session2_handoff_2026_07_25.md;
3. docs/release_experience_and_wine_card_roadmap_2026_07_24.md;
4. docs/session_2_5_release_experience_start_prompt_2026_07_29.md;
5. фактические Session 2.5 ТЗ, QA и handoff, созданные при её реализации;
6. docs/session_2_6_release_aware_offers_start_prompt_2026_07_29.md.

Если Session 2.5 не имеет статуса verified владельцем, её handoff отсутствует или
рабочее дерево содержит незавершённую реализацию 2.5 — не начинай миграцию offers:
сначала зафиксируй конкретный блокер.

Проверь актуальное дерево Git и коммиты после Session 2.5. Сохраняй любые
несвязанные пользовательские изменения. Документацию сверяй с кодом и живой
production-схемой.

Цель Session 2.6

Сделать магазинное предложение однозначным: конкретное вино → конкретный
релиз/винтаж → конкретный SKU/объём/упаковка → магазин, цена и доступность.
Исключить смешение цен разных лет и объёмов, сохранив чтение legacy-данных.

Обязательный объём

A. Полный аудит перед схемой
- Найди фактическую схему и все чтения/записи `offers`, `bottle_sizes`,
  `wine_product_codes`, `wine_vintages`, магазинов/sellers, cart/orders и связанных
  RPC/views/functions.
- Проаудируй пользовательские поверхности: карточка вина и релиза, каталог,
  поиск, карта, цены, предложения рядом, избранное, корзина/заказ и история.
- Проаудируй административные и seller-flow создания/редактирования предложения,
  импорты, seed/backfill, уведомления и аналитику.
- Составь dependency map: таблица/поле → writer → reader → UI → риск миграции.
- Посчитай production-данные: заполненность `offers.vintage`,
  `offers.bottle_size_id`, возможные соответствия `wine_vintages` и
  `wine_product_codes`, неоднозначности и orphan cases. Не изменяй данные во время
  аудита.
- Перед реализацией предложи точный целевой контракт и стратегию legacy fallback.

B. Целевая модель
- Новое предложение обязательно ссылается на `wine_id`, конкретный
  `wine_vintage_id` и конкретный SKU/товарный код либо эквивалентную нормализованную
  сущность, однозначно содержащую объём и упаковку.
- Предпочтительно переиспользовать `wine_product_codes`; не создавать параллельную
  сущность SKU без доказанной необходимости.
- Один GTIN может относиться к нескольким релизам одного вина согласно правилам
  Session 2; это не должно создавать ложный cross-wine конфликт.
- Цена, валюта, магазин, доступность и время актуальности остаются свойствами
  предложения. Год/NV, ABV и релизные фото не дублируются в offer.
- Объём/упаковка живут на SKU. Если исторические данные не позволяют определить
  SKU, сохраняй явное состояние unresolved/legacy, а не угадывай.

C. Additive migration и legacy
- Добавь nullable FK/поля и индексы без немедленного удаления
  `offers.vintage`/`bottle_size_id`.
- Новые записи после cutover должны идти только через новый контракт; legacy
  чтение временно использует документированный fallback.
- Сделай идемпотентный backfill только для однозначных совпадений. Неоднозначные и
  конфликтные строки вынеси в отчёт/очередь модерации, не связывай автоматически.
- Определи uniqueness и защиту от дублей с учётом seller, release, SKU и периода
  актуальности. Не полагайся только на UI.
- RLS/RPC должны разрешать нужные действия seller/admin и не открывать запись
  обычному пользователю.
- Все серверные функции должны иметь безопасный `search_path`, корректные grants
  и аудит изменяющих действий.

D. Seller/admin UX
- Flow создания предложения: выбрать вино → релиз (год/NV) → SKU/объём/упаковку
  → цену/доступность. Не разрешай сохранить неоднозначное новое предложение.
- Если нужного релиза нет, переиспользуй существующее предложение релиза и
  moderation-flow; не публикуй его автоматически.
- Если SKU/GTIN конфликтует с другим вином, покажи блокирующее предупреждение и
  путь к модерации. Несколько релизов одного вина обработай как выбор, не как
  ложный конфликт.
- Администратор должен видеть legacy/unresolved/offending предложения и способ
  безопасно довязать их к релизу/SKU.

E. Пользовательский UX
- В карточке выбранного релиза показывай только предложения, совместимые с этим
  `wine_vintage_id`; объёмы должны быть отдельными вариантами с собственными
  ценами и при необходимости фото.
- При смене релиза или объёма цена, магазин и доступность обновляются явно, без
  сохранения данных предыдущего выбора.
- В wine-level состоянии можно показывать агрегированный диапазон цен только с
  прозрачной подписью; нельзя выдавать цену другого релиза за цену выбранного.
- Карта и предложения рядом должны вести обратно к тому же release/SKU контексту.
- Корзина/заказ, если они участвуют в текущем продукте, сохраняют immutable
  snapshot release/SKU/volume/price и не меняются задним числом.
- Корректно обработай нет цены, одну цену, несколько магазинов, несколько объёмов,
  архивный релиз/SKU, устаревшее предложение и legacy fallback.

F. Границы
- Не реализуй оплату, новый marketplace, комиссии, логистику или полный Cellar Pro.
- Не начинай Session 3, не добавляй пользовательский Copilot и внешние search API.
- Не удаляй legacy-поля в этой сессии.
- Не меняй принятую в Session 2.5 публичную иерархию карточки и политику фото без
  отдельного доказанного дефекта.
- Не публикуй пользовательские релизы, GTIN или фотографии без модерации.

G. Миграции и production
- Перед любой production-миграцией: полный backup, SHA-256, dry-run
  BEGIN/ROLLBACK, apply и post-check. Сохрани пути и результаты в handoff.
- Проверь explain/index-план ключевых запросов и отсутствие N+1 для списков цен.
- Подготовь rollback/compatibility plan: старый клиент должен продолжать безопасно
  читать данные во время staged rollout 1.1.0.
- Admin web после готовности можно собирать и деплоить без дополнительного
  согласования. APK/AAB/IPA не собирай: Android APK собирает владелец; магазинные
  артефакты готовятся после приёмки Session 2.6.

H. Проверка и приёмка
- Добавь тесты схемы/RPC/RLS, идемпотентного backfill, duplicate guards,
  unresolved cases и legacy fallback.
- Добавь unit/widget/integration-тесты выбора release/SKU, смены объёма, цены,
  seller/admin flow, карты и order snapshot, если затронут.
- Повтори критические регрессии Session 2 и Session 2.5: три вида поиска,
  карточка/селектор релиза, add-bottle, погреб, модерация и фотографии.
- Проведи targeted analyze; полный analyze сравни с существующим baseline.
- Создай отдельную ручную QA-матрицу Session 2.6 для web/Android/iOS и ролей
  guest/user/seller/moderator/admin.

I. Документация, handoff и release readiness
- Создай отдельные Session 2.6 ТЗ, QA-матрицу и handoff.
- Зафиксируй целевую ER-модель, compatibility period, миграции/backups, backfill
  statistics, unresolved rows, коммиты, deploy и известные ограничения.
- Обнови roadmap и журнал. Не объявляй Session 2.6 verified до ручной приёмки
  владельцем.
- После приёмки подготовь единый release checklist версии 1.1.0 для RuStore и
  App Store: version/build numbers, Android/iOS artifacts, release notes,
  store-install smoke, staged rollout/monitoring и Git release tag.
- После фактического завершения сделай отдельный коммит только файлов Session 2.6;
  не push и не публикуй магазины без явной команды владельца.

Начни с read-only аудита схемы, данных и всех consumers. Затем дай evidence-backed
план и рекомендуемый additive контракт. Не приступай к production-миграции до
согласования целевой модели и backfill-правил.
```
